# 不吃亏 / Buchikui

> 消费前多看一眼，消费后少走弯路。

**不吃亏**是一个面向普通消费者的公益型行动指南：不做情绪曝光，不替用户“吵架”，重点帮助用户把消费纠纷变成一条可验证、可推进的证据链。

## 产品与体验规范

后续产品、内容、交互和视觉修改默认以以下两份文档为验收基准：

- [`docs/product-experience-spec.md`](docs/product-experience-spec.md)：**上位 SPECS**，定义完整产品感、信息架构、视觉层次、场景与内容质量、移动端、反退化规则和 Definition of Done。
- [`docs/design-system.md`](docs/design-system.md)：**视觉实现规范**，定义颜色、字体、组件、响应式、动效与无障碍细节。

任何面向用户的修改都应先满足 Product Experience SPECS，再进入具体视觉与代码实现；不要只以“代码已完成”或“单个组件看起来没问题”作为完成标准。

## 当前 Demo

首页现在是一套 **随机 Case 阅读器**：

- 直接访问首页时，每次加载从现有 Case 中随机展示一份；

### CASE 001：如何租车维权

租车页采用 **用户场景优先 + 证据链**：先让用户找到自己正在经历的问题，再直接回答“关键事实是什么、现在做什么”，而不是先要求理解完整合同或责任体系。

当前按租车过程覆盖 8 个入口：

1. **平台 / 授权门店**：在支付宝租车、携程租车、滴滴租车等入口下单，不等于平台就是实际出租方；同时甄别经营主体、合同出租方、收款方和实际交车方
2. **到店没车**：保留“无法按订单提供车辆”的真实履约状态，先别主动改成“用户取消”
3. **临时换车**：订单、合同、实际车辆、车牌、行驶证和保险 / 保障信息必须能对应
4. **又让我买保障**：比较平台与门店方案到底新增了什么责任，不按“无忧 / 全险”等名称判断
5. **还车被验损**：先对比取还车连续视频，再要求具体损伤、责任、定损 / 维修项目和金额依据
6. **信用免押被扣**：先拆开“是否应承担车辆损失”与“平台是否有权直接划扣”两个问题
7. **出险被拒赔**：先取得书面拒赔 / 不承担理由，再核对实际车辆、使用性质和承保 / 保障信息
8. **违章又收费**：官方交通违法处理与门店“待处理费 / 管理费”分开核对

证据仍保持 8 项，但不再暗示用户一次全部准备：页面按 **先留主体 / 订单 / 沟通 → 取还车时留车辆与车况 → 扣款或事故后再补保障 / 授权 / 定损材料** 三组呈现。

维权路径明确分工：**实际出租方 + 平台同步留痕 → 租赁经营 / 履约问题走 12328 → 押金 / 收费 / 格式条款等消费争议走 12315 → 仍无法解决再评估诉讼**。交通违法和事故责任本身另行区分公安交管事项。

移动端把原来的横向场景轨改为两列问题选择器，并把固定主行动改为“找到我的问题”；打印仍保留在证据区，不占用全程最重要的移动操作位。

### CASE 002：如何美容美发纠纷维权

覆盖 6 个高频场景：

1. 办卡 / 充值后退费争议
2. 低价引流后临时加价
3. 未经明确同意擅自加项目、换产品或换服务人员
4. 烫染、护理后出现过敏、灼伤、断发或皮肤损伤
5. 搬店、转店、换经营主体、闭店后旧卡无法正常使用
6. 生活美容越界开展医疗美容项目

### CASE 003：如何追讨银行小额账户管理费

这是第一个 `compact` Case，只保留 1–2 屏：

1. 先判断账户是否属于应免收账户，尤其核对 2017 年 8 月 1 日之后的唯一账户收费
2. 拉出小额账户管理费 / 账户管理费 / 年费扣费明细
3. 向银行申请核查并退回不应收取的费用，保留工单号和答复
4. 银行无法合理解释或拒绝处理时，通过 12378 继续投诉

### CASE 004：如何降低通讯套餐费用

通讯套餐页把长期老用户与新用户、活动渠道之间显著且持续的资费差直接作为 **价格歧视** 问题处理，目标不是讨论概念，而是把实际月费降下来。

覆盖 4 个入口：

1. **旧套餐太贵**：对比近 3 个月真实用量和当前低价方案；官方渠道查资费，小红书等用于发现套餐名、附加优惠和办理经验
2. **客服说办不了**：对“停售 / 仅限新用户 / 没权限”要求具体限制、同档替代方案、正式工单和上级处理
3. **携号转网**：保留原号码转入其他运营商，利用新入网套餐重新获得更合理的价格；先查询资格和现有合约 / 业务限制
4. **保号 + 新卡**：老号码降到当前可办理的最低月租 / 保号型方案，新卡承担主要流量；5 元、8 元等低价档位以实际可办理结果为准

证据清单只保留 6 项：近 3 个月账单、当前套餐与合约、真实用量、目标套餐 / 优惠页面、客服工单、携号转网资格短信。

页面给出四步降费闭环：算清用量并找到低价方案 → 正式申请变更并升级工单 → 必要时走工信部电信用户申诉 → 携号转网或保号 + 新卡。

### CASE 005：如何在互联网法院为自己打官司

这是一份面向第一次自行参加普通民事诉讼用户的 **诉讼行动指南**。页面先区分“在线诉讼”和“互联网法院”：能网上立案、在线交换证据或在线开庭，不等于案件一定归北京、杭州、广州互联网法院集中管辖。

当前覆盖 10 个第一次诉讼最容易卡住的节点：

1. **是否值得起诉**：先写清想让法院判什么、争议金额、最强证据、对方主体与可执行性
2. **互联网法院 / 网上立案**：先核对当前集中管辖范围，不因为交易发生在网上就直接选择互联网法院
3. **被告和管辖**：明确告谁、为什么这个法院有权管；自然人身份证号不是“明确被告”的唯一条件
4. **起诉状怎么写**：目标是减少补正，让当事人、具体请求、事实理由、管辖和证据一眼可见
5. **诉讼请求**：把“主持公道”改成能够直接进入判决主文、能够计算和执行的请求
6. **证据怎么整理**：证据编号、来源、证明目的和待证事实一一对应，电子数据保留完整上下文与原始来源
7. **证据在对方手里**：符合条件时申请法院责令提交具体书证，而不是笼统要求对方“交全部资料”
8. **追加被告 / 第三人**：当事人可以申请追加必要共同诉讼当事人，但是否追加及以何种身份参加由法院审查决定
9. **怎么质证**：围绕真实性 / 完整性、关联性、合法性、证明目的和证明力逐份回应，并准备反证
10. **开庭和判后**：庭审围绕 3–5 个争议焦点和对应证据；判后继续按裁判文书载明的期限处理上诉、履行和执行

证据区按诉讼阶段分成三组：**立案前先齐 → 举证阶段准备 → 庭审前再做**。页面同时提供一份可复制的民事起诉状骨架，但明确优先使用人民法院针对具体案由发布的现行要素式示范文本。

页面能力按 Case 复杂度使用：

- Standard Case：具体场景、证据清单、维权/处理路径、可复制模板
- Compact Case：判断条件 + 3–4 步行动路径 + 官方依据
- 所有 Case：随机首页、固定分享链接、打印、官方来源与免责声明

## 产品原则

- **场景优先**：用户通常从“我遇到了什么”进入，不要求先理解法律或责任分类
- **关键事实优先**：场景不是百科；只保留会改变用户判断和行动的事实
- **行动优先**：用户先知道下一步该做什么，再补背景知识
- **证据导向**：留下能证明主体、约定、授权、事实与金额的材料，不追求截图数量
- **按问题复杂度设计页面**：复杂问题允许更多入口，但单个入口保持短；简单问题保持 1–2 屏
- **渠道准确**：按纠纷性质区分平台、实际经营者、市场监管、行业主管部门、金融监管、卫生健康部门、公安交管和法院
- **去情绪化**：目标是退款、解除合同、取消收费、取得凭证或处理损害，不是“出口气”
- **公开可核验**：法规与官方渠道直接链接到政府 / 监管 / 法院来源

## 当前技术实现

继续保持纯静态站，不引入框架、构建系统或后端：

- `index.html`：统一页面壳
- `styles.css`：共享视觉系统
- `cases.js`：CASE 001–002 标准 Case 的结构化内容数据
- `compact-cases.js`：CASE 003 短 Case 内容数据
- `mobile-plan-case.js`：CASE 004 通讯套餐降费内容数据
- `court-case.js`：CASE 005 自助民事诉讼内容数据
- `app.js`：随机选择、standard/compact 渲染、证据状态与可选证据分组、Case 语义标签、分享、打印、复制模板
- GitHub Pages 直接部署

当前只有两种明确页面形态：`standard` 和 `compact`。不为每个 Case 单独复制页面，也不增加额外路由或框架。

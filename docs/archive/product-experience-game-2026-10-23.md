> 状态：Normative
> 更新：2026-10-23

## 0. 本轮已确定的产品决定

以下决定由现行契约与本轮用户指示确定。当前采用纸牌流程、八道真实个案改编题、三个情境组及书式目录，后续按实际体验迭代。

| # | 决定 | 既定规则 | 影响面 |
| --- | --- | --- | --- |
| 1 | CASE 是否保留独立 URL | **保留** `/c/<slug>/`，改变页面形态而非合并页面 | canonical、sitemap、预渲染、SW、外链 |
| 2 | 能否在答错或未答时继续 | **不能**：答错直接解释，在原题重选；答对才解锁继续 | 刷卡状态与前进条件 |
| 3 | 题目反馈落在哪里 | **GitHub issue**（预填标题）；消费者经历仍走 Supabase 队列，两者不混 | 反馈闭环、AGENTS.md |

## 1. 产品定义

“不吃亏”是一个**“不花钱也买教训”的消费场景游戏平台**。消费普法是内容底座，游戏是用户首先接触和参与的体验。

对读者的核心价值是：**不花钱，也能买到教训。** 通过可重试的情境选择，提前看见日常消费中容易忽略的事实、行动后果与判断边界。消费信息不对称、交易套路与行业规则等社会议题，通过具体、可核验的情境进入公众讨论。

设计重心放在题面的真实诱因、选择后即时看见的后果与解释，以及克制准确的交互和视觉。游戏体验由滑卡、即时反馈和连续经历形成，保持操作简单；本轮不引入分数、等级、成长收集或选题面板。

它不替用户做 AI 式纠纷诊断，不提供维权工具箱，也不做法条百科。它从公开、可核验的权威材料里
提取现实交易中最容易忽视、但会改变结果的关键点，然后让读者在**真实情景里做出选择**。

核心链路只有一条：

> 现实交易情景 → 权威依据 → 关键事实 → 现实提醒。

产品打开即玩：给出一个具体情景和一项行动，玩家左右选择会不会这样做，立即看见这一步可能带来的后果、解释与依据。
资料库没有消失，它从首页移到了导航和目录里，并且被重新组织成一本可以顺序读的书。

## 2. 首页：一张情景卡

### 2.1 首屏结构

```text
导航入口（品牌、资料库；具体布局待原型评审）
──────────────────────────────────────
情景卡（主界面，居中，最大视觉权重）
  情境与一项待判断的动作：合计目标 ≤ 80 字
  左滑 NO / 右滑 YES，同时有等价圆形点击按钮
  ─────────────────────────────────────
  当前状态动作 + 低权重依据 / 问题纠错入口
──────────────────────────────────────
资料库经导航可达；首页具体导航与目录布局以完整原型评审为准
```

首屏必须同时可见：品牌与一句定位、情景卡、以及卡上的按钮。**不使用弹窗**：
弹窗同时踩三条线——首屏规范、390px 无溢出、无障碍焦点陷阱。

### 2.2 题目数据结构

题目、编排与审核状态在 `editorial/game-content.json`，经校验进入SQLite数据库，再导出 `content-data.js`；`scenario-checks.js`只管理判定与状态。本地读取数据库公开接口，静态部署或离线读取同库快照。流程见 `content-database.md`。

每题包含：题号、章节和规则ID、真实案例ID、改编性质、审核状态、可能误判的原因、现场事实、短问句、答案方向、两种选择影响、简短解释和适用边界。情境与问句合计不超过80字。

**答案只能来自 `legal-updates.js` 已有的依据**，不得为题目另立一套说法。公开题必须绑定已核验真实个案，而且对应规则须直接引用该个案。旧校准题在数据库中标为退役，不进入公开载荷。

### 2.3 卡片状态机

```text
待判断 ──左右滑 / 点击──> 答错 ──直接解释──> 原题重选
   │                                        │
   └────────────正确选择──────────────────────┘
                    ↓
                  答对 ──显示理由与适用边界──> 解锁继续 ──主动点击──> 下一张
```

- 一张卡只判断一项具体行动：左滑 NO，右滑 YES；没有额外提交。
- 答错留在本题，解释自动可见，并允许立即重新选择；答对以前不能前进。
- 答对后主动点击「继续」才进入下一张，不自动跳走解释。
- 查看依据与资料库不改变判定；返回时恢复原题和原状态。
- 手势必须有等价点击、键盘操作；`prefers-reduced-motion` 下同样工作，不做 3D 旋转。

### 2.4 判定

- 选择后立即判定。正确选择用深红并标「正解」；方向本身不预先标成正确色。
- 错误解释指出关键事实和实际风险，仍可重选；不用羞辱性文案或叠加惩罚。
- 结果与必要解释用 `aria-live="polite"` 播报，不能只靠颜色区分。
- 判定用于让读者理解选择与依据，不给读者评分。

### 2.5 就地解释

答错后直接显示为什么错、可能造成什么后果，以及更合适的行动，留在同一张卡重选。
答对后显示正解、简短理由与适用边界，并解锁继续。

两种结果均先显示“这个选择之后”与一条具体影响，再显示理由和边界。`outcomeCorrect` / `outcomeWrong` 为必填，目标约 15–25 字、硬上限 30 字；风险使用“可能 / 容易”等措辞，不把模拟选择说成玩家已经被扣款、已经违法或必然胜诉。这些短句随题目一起参与版本指纹，改动后重判。

解释与边界合计目标 ≤ 150 字；情境事实继续保留，正确行动在答对时突出呈现。完整法源通过对应 CASE 的 `#rule-<ruleId>` 查看。
**什么时候不适用不可省**，不把正确行动写成现实中必然获胜或免损的保证。

### 2.6 题序

- 打开首页直接出现可判断的情境；不先要求完成主题筛选。
- 当前题只有答对后才可继续，不提供跳过或未答换题旁路。
- 当前八题分成三个情境组：客房款两题 → 预付消费三题 → 售后三题。组内是相关的独立公开纠纷，不冒称同一个人的连续真实经历；一组结束后主动点“再遇一件事”进入下一组，第三组后循环。
- 分享可从指定题的未答状态进入，只接着走完该段后续情境；结束后仍可进入下一段。刷新与查依据返回保留当前段、题目和判定；规则或题面更新时不沿用旧正解。
- 每张卡背后仍是一个固定地址的固定章节；查看该章节不等于答对。

### 2.7 卡片动作

| 按钮 | 行为 | 落点 |
| --- | --- | --- |
| NO / YES | 等价于左滑 / 右滑，待判断与答错状态可用；读屏同时说明否 / 是 | 同题判定 |
| 继续 | 只有正确选择后可用；主动进入下一张 | 下一张 |
| 再遇一件事 | 仅在当前段结束时可用；主动进入下一段，第三段后循环 | 下一段首题 |
| 查看依据 | 阅读对应规则与完整主题，返回时恢复状态 | 固定章节的规则锚点 |
| 这题有问题 | 打开预填标题的 GitHub issue | 仓库 issue |

判断 / 继续是当前状态的主动作；依据和纠错保持低权重，不增加一串中间确认按钮。

### 2.8 题目反馈

「这题有问题」是**对仓库内容的纠错**，走 GitHub issue（预填题号与选项），不带入消费者经历队列。
消费者亲历与信息纠错仍走 `docs/consumer-feedback.md` 定义的 Supabase `product_feedback` 管线。
两者是不同的对象，不进同一个队列，也不互相当作对方的入口。

## 3. 导航

首轮导航沿已批准流程稿收敛：

- **不吃亏**：回到当前情境；
- **资料库**：合并电子书式目录与关键词搜索，原有多维筛选收进“按条件筛选”；
- **返回当前情境**：资料库和章节中有保存进度时可见，章节顶部导航始终可达，查规则后直接返回；
- **这题有问题**：位于卡片辅助位置，指向预填 GitHub issue，不在顶部重复增加反馈入口。

导航是资料库与决策卡之间的唯一通道。不要在导航里放 Dashboard 指标、完成度或推荐位。

## 4. 目录：一本书的目录

- 目录页把全部主题按**卷 / 章**编排，而不是按平行分类平铺；
- 每章一行展示章序、短标题和现实问题；来源类型、核验日期与更新信息进入章节查看；
- 目录同时是内容索引、阅读路径与对外的可读目录；它由数据生成，不手写；
- 首轮采用的卷序由 `book-order.js` 提供，正文与现实问题仍来自既有 CASE：

| 卷 | 主题 |
| --- | --- |
| 一、把钱要回来 | 租车 · 信用卡预授权 · 预付消费 · 小额账户费 · 银行理财 · 投顾费用 · 拍卖 |
| 二、平台与商家 | 套餐 · 家电维修 · 机场推销 · 网约车与货运 |
| 三、人生转折 | 被裁与补偿 · 相亲安全 |
| 四、远行与境外 | 泰国旅行 · 青岛旅游 |
| 五、自己去打 | 第一次自己打民事官司 |

卷序只表达**阅读先后**，不表达重要性，也不参与筛选维度。

## 5. CASE = 书的一章

### 5.1 地址

`/c/<slug>/` 继续是唯一规范地址。形态改成书的一章：顶部有目录入口与章序，
底部有上一章 / 下一章，页面本身仍是这一章的完整正文。

合并不删除地址。理由：canonical、sitemap、预渲染正文、结构化数据与已被分享的链接都已经存在，
删除它们等于一次性丢掉搜索与分享资产，而“像书一样读”并不需要这个代价。

### 5.2 章内结构

> 现实问题 → 权威依据 → 现实交易提醒 → 证据与处理路径（按需） → 原文 → 一句可迁移经验

章序以中文数字 + 题目呈现（如「第三章 · 家电维修」）。
**章序与内部 id（`001`、`002`）是两件事**：章序是给读者看的编排，internal id 不进入任何用户可见位置。

### 5.3 首章

打开任意一章时，页面必须能让读者立刻回答：这一章在讲什么现实问题、答案在第几节。

## 6. 题目纪律

判对错是这个产品里风险最高的交互，因此以下为硬约束：

1. **每题必须挂 `ruleId`**，答案必须是 `legal-updates.js` 里现行有效的依据；
2. **每题必须写 `exception`**，写清什么时候不适用；
3. **每题判断一项行动或一项具体主张**，左右始终回答题面是／否。必须有足够事实支持明确二选一；条件不清或有争议的内容保留在章节解释，不硬设唯一正解；
4. **题目随依据复核**：依据的 `verified` 变更时，同步复核该题；
5. **禁止题型**：与真实交易无关的常识题、靠记忆年代或数字的选择题、把法条原文当选项的题、
   选项之间表述不平行（一个含具体金额、一个不含）的题；
6. **禁止语汇**：维权神器、必胜、避坑、教你一招、千万注意、否则血本无归；
7. 题量服从内容质量，不设最低数量门槛。用户指出原十二题缺少真实判断价值后，六道校准题已退役，当前为八道个案改编题、三个情境组。保留具体事实与可核对的争议点，不能为达标填题；是否有趣、是否贴近经历仍需试玩验证。
8. **现场感**：写出谁在此刻对你说了什么、眼前要完成哪一步；行动用可直接回答 YES / NO 的短问句。避免把“问清方式、程序和时限”一类规则总结直接当作大字题面，也不只靠增加催促或等待来制造情境。
9. **现实性评审**：优先真实纠纷的关键事实；规则应用的合成场景要如实记为改编，不能冒称真实案例。不编反常的“坏人台词”提示答案，不把“先问清／留证”设成万能正解。允许围绕一项具体判断问是／否；读屏使用相同语义。撤下事实不足或多个合理答案的题，不通过语气暗示正解。
10. **选题标准**：优先反常识、容易误判、典型且有代表性的真实消费场景，以简洁题面呈现。先找到真实争议及人会误判的原因，再提炼一个问题；不靠隐去关键条件制造反转。是否易错、是否愿意互动须通过试玩验证，不把编辑直觉当成用户证据。候选与来源边界见 `scenario-candidates.md`。

## 7. 权威依据

用户可见名称统一使用：

- **权威依据**：法律、行政法规、司法解释、部门规章、监管文件、监管通报等；
- **裁判参考**：指导案例、典型案例、监管处罚案例、普通裁判等。

必须明确：来源类型、机关 / 法院、文件 / 案号、生效或裁判时间（如有）、核验日期、原文链接。
媒体转载官方通报时，标题如实标注为媒体报道，不得写成官方原文。
Buchikui 的解释不能伪装成法条原文；普通裁判不能被写成普遍法律规则。

## 8. 视觉语言

游戏首页以单张可操作情境卡为中心，纸张感、强排版、少按钮，让选择和反馈形成节奏。资料库与章节保持可信的编辑型阅读界面。

单卡是游戏的主要交互形态。资料库仍以标题、细线、列表、文献式元信息为主。

避免：大面积彩色卡片、发光按钮、仪表盘、数字进度、成就、连续天数、排行榜、AI 助手口吻。

**允许的游戏感**：连续情境、左右刷卡、必要回弹、就地解释、判定红标、答对后继续。
**禁止的游戏化**：分数、等级、进度条、成就徽章、连续天数、排行榜、分享得分。

## 9. 移动端

390 px 宽度必须：

- 无横向溢出；
- 首屏可见品牌定位、情景卡与卡上按钮；
- 情景卡在窄屏上按「事实与行动 → 解释（判定后）→ 当前状态动作」组织；
- 两个判断动作及继续的触摸目标 ≥ 44px；
- 查看依据与问题纠错的触摸目标 ≥ 44px，视觉保持弱化；
- 权威依据允许纵向堆叠；
- 无固定底部双 CTA。

## 10. Definition of Done

发布前检查：

1. 打开首页是否立刻出现一张情景卡，且不需要任何操作；
2. 左右滑、点击和键盘是否语义一致，选择后是否立刻判定且不需要提交；
3. 每题是否都挂到现行依据，每题是否都写了什么时候不适用；
4. 答错是否自动解释并留在原题重选，解释与边界是否简短、没有营销词；
5. 是否只有答对才解锁继续，查看依据后是否恢复原题和原状态；
6. 导航能否到达搜索、目录、反馈；
7. 目录是否按卷章编排，且由数据生成；
8. CASE 是否仍是固定地址的独立章节；
9. 页面里是否出现分数、进度、成就或排行榜；
10. 有没有仍然像“AI 给我做诊断”的模块？有则删除；
11. 权威依据与 Buchikui 的现实翻译是否仍清楚分离；
12. 原文能否直接打开；
13. `node scripts/check-frontend-contract.mjs` 是否通过。
14. 八题能否走完三个情境组，并用“再遇一件事”继续；各组分享是否从对应题未答开始，返回与刷新是否恢复原状态。

真实手机触摸、读屏、系统分享与普通用户试玩按 `release-acceptance.md` 执行并记录证据，未执行的项目保持待验收。

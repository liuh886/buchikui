# 不吃亏 / Buchikui — CASE Content Standard

> 状态：Normative  
> 适用范围：新增 CASE、修改既有 CASE、吸收消费者反馈  
> 目标：**页面尽量简单，但不能漏掉未来决定投诉、责任认定、证据采信、损失金额或判决结果的关键步骤。**

## 1. 核心原则

### 1.1 简化表达，不简化关键流程

可以删背景解释、重复提醒和百科式知识；不能为了页面更短而跳过关键事实节点。

统一判断：

> **能删解释，不能删关键步骤；能合并表述，不能跳过闭环节点。**

### 1.2 争议焦点保留与补齐测试

编辑现有 CASE 时，不只检查“有没有把关键步骤删掉”，还要倒推一次：

> **如果未来发生投诉、调解或诉讼，对方、监管机构或法院最可能追问什么？页面现在有没有帮助用户提前固定这些事实？**

一个步骤只要未来可能回答下面任意问题，就必须保留；如果当前 CASE 完全没有覆盖，也应补齐：

- **谁负责？** 实际经营者、合同相对方、平台、收款方、履约方是谁；
- **事前说了什么？** 价格、服务、授权、免责、交付或退费 / 扣款规则是否提前告知；
- **什么时候发生？** 告知、交付、异议、损伤、扣款、投诉等先后顺序；
- **当时是否确认或异议？** 是否签字、点击授权、当场指出、要求补记或书面反对；
- **损失从哪里来？** 是既有问题还是本次服务造成，因果关系能否区分；
- **金额怎么算？** 收费、维修、赔偿或损失是否有项目、计算和实际凭证；
- **有没有核验和申诉机会？** 对方是否说明依据、提供材料并允许消费者提出异议；
- **有没有会让权利或程序直接失效的期限 / 后续确认？** 例如补正、缴费、申诉、上诉，或者变更服务后的生效与首笔账单核对。

如果删掉某一步会让未来出现“你怎么证明？”、“对方当时有没有告诉你？”、“你当时有没有提出？”、“这笔钱怎么算？”、“你有没有按时完成下一步？”而页面无法回答，这一步不能删。

## 2. Standard CASE 的默认结构

保持现有最小闭环：

**一句主张 → 3–4 个立即动作 → 找到我的问题 → 场景 → 关键证据 → 处理路径 → 可复制模板 → 来源**

不是每个 CASE 都必须增加额外模块。只有确实帮助用户判断时才增加，例如“正常服务基线”。

### Hero

只做两件事：

1. 用一句主张说清这个 CASE 的核心问题；
2. 用一小段说明真正决定结果的关键链条。

不要在 Hero 里完成全部法律解释。

### Immediate Actions

通常 3–4 项。每项尽量写成：

**对象 + 动作 + 要得到 / 保存的结果**

避免“注意留证”“依法维权”“与商家协商”等空泛表达。

## 3. 场景是主要写作单位

每个 Standard CASE 场景默认只保留：

### 关键事实

回答：

> **什么事实会改变我的判断？**

只保留真正决定责任、证据或下一步动作的事实。法规、判例和专业解释必须服务于这个判断，不写成小论文。

### 现在做什么

回答：

> **我现在具体应该做什么？**

默认写成一个简洁段落；但如果多个动作有先后依赖，必须按真实顺序全部保留，不能为了“一句话”而漏步骤。

例如取还车验损可以保持为一个场景，但关键顺序不能丢：

**经营者说明已有损伤 → 双方核对车况记录 → 漏标当场补记 → 消费者独立留影 → 还车按同一范围再次留证 → 发生索赔后要求损伤、责任和金额依据。**

## 4. 证据与路径

### Evidence

证据不是材料名堆积。优先保留真正会改变结果的材料，并说明它解决什么问题。

如果有明显时间顺序，优先按：

**现在先留 → 现场再留 → 发生争议后补**

来组织。

### Route

每一步尽量回答：

**什么时候升级 → 找谁 → 带什么 → 要什么结果**

Route 还必须包含必要的闭环确认。例如服务已经变更，不应停在“客服说办好了”，还要核对实际生效状态和下一笔账单；诉讼已经立案，也不能漏掉法院通知中的补正、缴费和后续期限。

不要只写“协商不成可以投诉”。

## 5. 法律、案例与操作建议

只保留一个表达原则：

> **法条只写法条明确规定的；案例只写案例实际认定的；我们的操作建议明确写成操作建议。三者不要混成同一种确定性。**

个案判决不得直接泛化成所有类似纠纷的必然结论。

## 6. 新信息与消费者反馈怎么进入正文

默认顺序：

1. **先替换弱表达；**
2. **再合并进已有关键事实 / 行动；**
3. **只有确实改变用户判断、行动、证据或处理路径时，才新增场景或模块。**

消费者反馈是发现现实问题的线索，不是自动成立的事实规则。涉及法律、监管、平台政策、收费、医疗、保险、法院程序等内容，发布前仍需核验当前可靠来源。

不要把每条新经验 append 到正文，避免 CASE 随时间不断膨胀。

## 7. Compact CASE

简单问题继续使用 Compact：

**一句主张 → 判断 / 条件 → 3–4 步处理 → 必要模板 / 说明 → 来源**

不要为了形式统一强行补齐 Standard CASE 的所有模块。

## 8. 发布前只检查这 5 件事

1. 用户是否能快速知道自己遇到了什么问题？
2. 每个场景是否仍以“关键事实 + 现在做什么”为主？
3. 有没有漏掉未来可能决定投诉、责任认定、判决结果或程序能否继续的关键步骤？
4. 有没有可以删掉的重复解释、背景知识或弱提醒？
5. 新增内容是否真的改变了判断、行动、证据或处理路径？

如果第 3 项答案是“有”，不能发布。

---

一句话标准：

> **短而完整：保留并补齐未来会成为争议焦点的事实和动作，删除不改变用户判断与处理结果的解释。**

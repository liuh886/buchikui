# 不吃亏 / Buchikui — CASE Content Standard

> 状态：Normative  
> 适用范围：全部现有 CASE、新增 CASE、CASE 重写、消费者反馈吸收  
> 修订依据：2026-09-02 全站三轮编辑整改  
> 核心目标：**一个 CASE 只解决一个核心问题。每一句都要增加事实、判断或动作，不用模板话替代内容。**

## 0. 写之前，把问题想明白

不要从“有哪些法律”开始。先回答四个问题：

1. **消费者为什么容易吃亏？** 他具体少知道了什么？
2. **谁控制关键东西？** 钱、证据、规则、决定权分别在谁手里？
3. **哪个动作一旦顺手做掉，以后最难补？** 例如主动取消、确认无异议、继续付款、接受新协议、让旧件被带走。
4. **如果很多消费者都照这页去问，对方最需要因此改进哪个流程？**

第 4 项是编辑研究问题，不要求每个 CASE 都展示为 Discussion。

## 1. 唯一主命题

每个 CASE 发布前必须写出一句话：

> **这个 CASE 最希望用户下次改变哪一个选择或动作？**

这句话就是页面唯一主命题。Hero、立即行动、场景、Evidence、Route、权利校验、Discussion 和 Takeaway 都不能与它争夺主线。

如果一页同时回答两个互不从属的问题，拆分 CASE；如果第二个问题只是例外、补救或出事后的处理，把它降到主线后半段。

禁止：

- 标题给一个结论，正文主要讲另一个问题；
- 同一结论换 3–4 种说法重复出现；
- 用法律维度作为页面目录；
- 为了形式整齐硬凑“四原则 / 五问题 / 六法律点”。

## 2. 默认阅读顺序

Standard CASE 默认：

**Hero → Immediate Actions → 权利校验 → 典型场景 → Evidence → Route → 按需 Template → 按需 Discussion → Sources / Disclaimer → Takeaway**

Compact CASE 默认：

**Hero → 约 3 个关键理由 / 条件 → 权利校验 → 3–4 步处理 → 按需 Discussion → Sources / Disclaimer → Takeaway**

模块不是必填表。没有内容价值就不加。

## 3. Hero：直接给判断

Hero 只做两件事：

1. 直接给核心判断；
2. 用 2–4 句说明为什么用户会在这里吃亏、本文准备解决什么。

优先写：人、钱、价格、授权、主体、证据、时间、动作。

好标题应当能直接回答一个问题，例如：

- **你付的钱，司机未必看得到。**
- **租车纠纷，先把谁履约、开什么车、为什么扣钱对清。**
- **阿里拍卖，先查谁在拍、谁在竞价。**
- **支付宝投顾，0.5% 不是总成本。**

Hero 不做：

- 不从法规名称、年份和政策沿革起笔；
- 不解释完整法律结构；
- 不堆“责任结构、权利位置、链路、机制、治理框架”等抽象词；
- 不提前塞进所有例外和免责声明；
- 不用“守住关键节点、提高警惕、分场景防范”替代具体风险。

判断标准：普通消费者只看 Hero，也能用自己的话复述“这件事到底要小心什么”。

## 4. Immediate Actions：告诉用户现在别做错什么

通常 3–4 项，只放跨场景最优先的动作。

优先使用：

> **对象 + 动作 + 要得到 / 保存的结果**

尤其优先写那些**现在不做，以后很难补**的动作。

好例子：

- 商家没车，不要自己点“用户取消”；
- 电话结论马上转成文字；
- 第一次换件没修好，先停，不要继续换 B、C；
- 要扣钱，先要事实、条款和金额依据；
- 被阻止离开或遭到威胁，先离开现场并报警。

不要写：注意留证、依法维权、谨慎选择、理性消费、守住底线、提高警惕。

## 5. 权利校验：只负责关键点和法律法规

权利校验是全页法律密度最高的地方，但不是法规文章。

每一项必须完成：

**消费者问题 → 当前法律关键点 → 对方必须 / 不得做什么 → 现在可以要求什么 → 一手来源。**

例如不要只写：

> 《网络交易平台规则监督管理办法》规定平台应建立申诉机制。

应该直接写：

> **平台不能只回复“系统判定”。**

然后再给事实、理由、依据、人工复核等具体权利和法源。

权利校验使用单条还是 2–4 个 Tabs，**完全服从 `docs/legal-freshness-standard.md`**：默认单条；只有彼此独立、都足以改变消费者动作的关键权利问题才使用 Tabs。

不把法律新闻、政策愿景、边缘法规和普通个案堆进这里。

## 6. 分场景：典型问题 + 行动提示

场景是 Standard CASE 的核心单位。

场景标题必须像消费者会说的话：

- 到店没车
- 临时换车
- 做完才说要加钱
- A 换完没修好，又说 B、C 也坏了
- 还车以后突然被扣钱

不要用法规名、法律概念或“责任认定 / 合同效力 / 平台义务”作为场景标题。

每个场景默认只保留两块：

### 关键事实

回答：

> **这里哪些事实决定责任、金额、授权或证据判断？**

先给判断，再解释必要原因。法条只在确实帮助理解这个判断时出现。

### 现在做什么

回答：

> **我现在找谁、说什么、保存什么、要拿到什么结果？**

行动提示必须对应前面的关键事实，不能泛泛地说“投诉”“协商”。

两个场景如果判断和动作基本相同，就合并。

## 7. Evidence：不是材料仓库

Evidence 只保留直接对应争议焦点的材料。

每项默认：

**材料名 + 一句用途 + 确有价值时的保存时间。**

优先保留会证明：主体、明确同意、授权范围、价格、服务 / 损伤前状态、交易过程、实际损失、关键期限的材料。

Evidence 标题也必须有信息。优先直接列对象，例如：

- **产品文件、风险测评、推荐记录和购买页面**；
- **账号、见面地点、账单、转账和报警记录**；
- **第一次约谈、工作条件变化、PIP / 警告、持续出勤和最终解除**。

不要写“把事实固定下来”“把关键证据钉牢”“把购买当时还原出来”后就结束。若标题只说明“这里是证据区”，可以删掉或直接列材料。

如果关键证据在商户、平台、银行或机构手里，要明确写：

> **向谁索取什么。**

不要让消费者误以为所有证据都只能自己找。

## 8. Route：只负责升级路径

Route 不重新讲一遍法律和事实。

每一步回答：

> **什么时候升级 → 找谁 → 带什么 → 要什么结果**

Route 标题优先直接写分流关系，例如：

- **价格和经营争议找 12315 / 12345；人身威胁直接 110。**
- **先让入口平台和承运平台给出全链路费用表；解释不了再交 12328 / 市场监管。**
- **先书面谈方案和补偿；协商不成再调解、仲裁或监察分流。**

不要写“按有效路径处理”“按风险级别处理”“一步一步往上走”。这些句子只说明存在流程，没有说明流程是什么。

保留会影响受理、期限和救济结果的程序条件；普通背景说明删除。

不要把所有 123xx、监管机关和诉讼渠道都列出来。只列与本 CASE 的争议性质真正匹配的路径。

## 9. Template：把权利翻译成可以复制的话

Template 默认折叠，可有可无。

只有当一段标准化表达能明显降低用户沟通门槛时才加入。

模板优先包含：

- 可核验事实；
- 明确诉求；
- 对方需要提供的材料；
- 工单 / 书面答复要求；
- 新规则赋予的程序请求，例如人工复核、说明事实理由依据、提交其控制的证据。

Template 标题直接告诉用户这份材料要写什么，例如：

- **投诉时写明商户、订单、金额和具体行为。**
- **按时间列出每次诊断、换件、结果和收费。**
- **平台说不清差额，直接要一张完整账。**

不要写“把事实说清楚”“把感情纠纷改写成可核验事实”这类编辑说明。

不要写情绪宣泄式“律师函口吻”。

## 10. Discussion：可选，只讨论值得改进的机制

Discussion 是**可选末段模块**，位置在行动内容之后、Sources 之前。

它只回答：

> **这个 CASE 除了帮助一个消费者，还暴露了哪个值得产品、平台或行业改进的机制？**

适合讨论：

- 审核机制是否跟得上新的扣款能力；
- 争议中的证据是否过度掌握在单方；
- 平台是否需要更好的人工复核、通知或申诉；
- 新型业务在提供便利时，责任机制是否同步完善。

写法要求：

- 2–4 个短段落即可；
- 先写已确认的现状，再指出具体制度缺口，最后提出克制的改进方向；
- **现行法律要求**与 **Buchikui 的治理建议**必须明确区分；
- 不新增第二套维权步骤；
- 不为了“有观点”给每个 CASE 强行增加 Discussion。

避免编辑者站出来宣布观点：

- 不写“算法监管还需要继续细化”；直接写**现行规则还没有单独列明什么行为**；
- 不写“Buchikui 的治理建议”；直接写**建议增加哪项透明义务、审核责任或数据保全机制**；
- 不写“这个案例可复制的经验很明确”；直接写**哪些事实在后续争议中会成为核对起点**。

## 11. Sources / Disclaimer：负责可核验和边界

Sources 优先使用当前有效的一手 / 官方来源，并标明法源权重。

正文已经讲清楚的内容，不在 Sources note 里再写一遍长解释。

Disclaimer 只负责必要边界：什么不能从本页结论直接推出、哪些结果仍取决于具体事实。不要用免责声明冲淡正文已经可以成立的判断。

## 12. Takeaway：只留一个结论

每个 CASE 最后一条只回答：

> **用户离开页面后，最值得记住的具体判断或下次动作是什么？**

只能有一句，并与 Hero 的主命题首尾一致。

页面统一标签使用 **“本页结论”**，不使用“最后记住”“最终经验”制造额外强调。

Takeaway 不能突然升高到社会评论，例如“国家有规定，但消费者不监督就不会执行”；如果这句话不改变用户下一步动作，就删掉。

## 13. 法规只做支撑，不做目录

一条法规进入默认阅读层，必须至少改变下面一项：

- 用户现在该做什么；
- 对方必须说明什么；
- 谁应提供证据；
- 哪个授权 / 收费 / 履约行为是否成立；
- 责任或损失金额怎么判断；
- 投诉、申诉或诉讼应该找谁。

如果只能提供背景知识，放 Sources。

法源权重、效力核验、Tabs 准入和裁判引用纪律，以 `docs/legal-freshness-standard.md` 为唯一规范。

## 14. 只保留决定结果的关键点

一个事实或动作只有符合至少一项，才进入核心内容：

1. 会改变责任判断；
2. 会改变损失金额；
3. 会改变授权、收费或履约是否成立；
4. 会改变证据能否取得、接受或核验；
5. 会改变投诉、调解、诉讼或执行结果；
6. 用户现在不做，以后很难补。

核心纪律：

> **简化解释，不简化决定结果的过程。**

## 15. 去模板化：每一句都做信息增量测试

这是 2026-09-02 全站整改后新增的强制规则。

### 15.1 信息增量测试

对标题、过渡句、结尾逐句问：

> **删掉这句话，用户会少知道一个事实、一个判断、一个对象或一个动作吗？**

如果答案是否定的，删除。

典型应删：

- 守住关键节点；
- 分场景逐个防范；
- 每个场景只抓一个关键动作；
- 一步一步看；
- 按有效路径处理；
- 出现这些信号就要提高警惕。

它们可能语法正确，但没有告诉用户**节点是什么、场景是什么、路径是什么、信号是什么**。

### 15.2 可迁移句测试

再问：

> **这句话能否原封不动搬到另外 5 个 CASE？**

如果可以，通常说明它描述的是“文章结构”而不是“这个案例”。

例如“先留证据再选路径”“把关键事实说清楚”“事情发生后先做这些”，几乎可以放进任何消费纠纷，因此不应占据 Hero、Section、Route 或 Takeaway 的核心位置。

公共模板尤其要执行这一测试。加载占位只负责“正在载入”，不要趁机输出一套泛化消费哲学。

### 15.3 对象替代抽象词

看到以下词时，不是机械禁用，而是必须追问对象：

- 关键
- 节点
- 场景
- 风险
- 路径
- 机制
- 事实
- 证据
- 控制权

如果能直接写对象，就直接写：

- “守住四个节点” → **核验维修方身份、记录每次诊断、付款前核对账单、原故障未解决就复检**；
- “风险升级” → **目的地、交通或手机开始被陌生人控制**；
- “固定事实” → **保存账号、地点、账单、转账和报警记录**。

### 15.4 数字不是结构装饰

“四步、五类、六样东西、十个证据”只有在数字本身帮助记忆或确实构成完整集合时保留。

禁止为了页面整齐先定数字，再把内容硬塞进去。

判断方法：去掉“四 / 五 / 六”以后，标题是否更清楚？如果是，就去掉数字，直接列对象。

### 15.5 不重复上一屏

Hero、Immediate Actions、Section、Evidence、Route、Takeaway 各自有职责。

如果下一模块的标题只是把上一模块换几个词再说一遍，删掉标题或改成该模块独有的信息。

尤其禁止：

- Hero 说“注意价格”，Section 再说“分场景注意价格”，Takeaway 再说“最后记住价格”；
- Route 重复场景里的法律分析；
- Evidence intro 重复“要留证据”而不说明留什么。

## 16. 比喻、口号和情绪判断的准入规则

Buchikui 不禁止有记忆点的表达，但它必须承担信息功能。

### 16.1 比喻可以保留，但必须一一对应真实结构

允许：

> **支付宝投顾的真实交易成本犹如冰山。**

因为“露出水面的投顾管理费”与“水下的底层基金运作费、交易手续费”存在清晰、可计算的一一对应，比喻帮助用户理解费用叠层。

不允许：

- “风险像冰山”但没有说明水上、水下分别是什么；
- “守住红线”但没有法定或操作边界；
- “把事实钉牢”但下一句仍然不说保存什么。

**比喻后必须能立即展开成具体对象。展开不了，就删。**

### 16.2 口号不能替代结论

“安全第一”“理性消费”“捡漏你就输了”可以有传播性，但如果它遮住真正需要记住的动作，应把动作升到主标题。

例如：

- “相亲约会：安全第一” → **第一次见面保留随时离开的能力**；
- “捡漏你就输了” → **先查谁在拍、谁在竞价**。

### 16.3 删除无证据的情绪判断

不要用：

- “求饶会助长对方嚣张”；
- “风险级别直接拉满”；
- “这是最恶劣的套路之一”——除非比较范围和证据明确。

改成可观察动作与处置条件：**辱骂、尾随、阻拦离开、暴力威胁出现时，拉开距离、去有人处、报警。**

### 16.4 避免不必要的绝对化动作

“一定要买就全程录像”“任何情况下都……”容易制造新的模板建议。

只有法律义务、安全处置或事实条件足够明确时才使用绝对词。一般消费场景优先写触发条件：

- 口头承诺较多时录音；
- 有现实人身危险时直接报警；
- 第一次换件未解决原故障时先停。

## 17. 语言纪律

Buchikui 的文字要像一个熟悉消费纠纷的人直接说明问题：短、准、具体。

默认顺序：

> **结论 → 关键事实 / 规则 → 动作**

要求：

- 三句能说完，不写五句；
- 一段只解决一件事；
- 法律名称放在消费者结论之后；
- 能说“谁扣了多少钱”，不说“资金控制结构”；
- 能说“要求平台给出商户材料和审核依据”，不说“推动证据流动”；
- **禁止用“不是……而是……”作为固定论证骨架。** 法律上确实需要区分两个概念时，直接分别陈述两者效果；
- **避免“先确认…… / 先确定……”成为模板式标题。** 只有真实时间顺序存在时才使用“先”，例如先停、先保存、先报警；
- 删除正确但无用的句子；
- 删除编辑元话语：本文只看、下面分别讲、按你遇到的问题找、我们进一步讨论、这个案例说明了一个道理；
- 删除没有信息增量的总结腔：真正要看的是、真正要记住、最重要的是、最关键的是、说到底、归根结底、本质上、换句话说；
- 需要强调时，强调**对象和差异**，不强调“我认为这很重要”。

判断方法：删掉“真正 / 关键 / 最重要 / 讲明白”后，如果事实和动作完全不变，就删掉这些词；如果整句只是在告诉读者“下面我要解释什么”，整句删除或改成结论。

## 18. 公共模板与组件文案

CASE 文案改干净后，公共组件不能重新制造统一腔调。

要求：

- 加载占位只写加载状态，不输出“先留证再维权”之类理念；
- Discussion 没有 intro 时允许为空，不使用全站统一的“从这个 CASE 再往前一步”；
- Footer 可以有品牌信息，但不要再总结一套适用于所有 CASE 的空泛行动哲学；
- “处理路径、可直接复制、本页结论”等功能标签可以统一，因为它们承担导航功能；内容标题不能统一套话。

**组件可以标准化，结论不能模板化。**

## 19. 发布前验收

每次新增或修改 CASE，逐项回答：

1. 能否用一句话说出唯一主命题？
2. Hero 是否直接说了本案例的对象、差异或动作，而不是法规摘要或口号？
3. Immediate Actions 是否指出现在最容易做错、以后难补的动作？
4. 权利校验是否只保留真正改变动作的关键法律点，并符合 Legal Freshness Standard？
5. 每个场景是否真的是高频典型问题，并且只有“关键事实 + 现在做什么”？
6. Evidence 是否直接说要保存什么，而不是只说“留证”？
7. Route 是否直接说找谁、何时升级，而不是“按路径处理”？
8. 是否保留了会改变责任、金额、授权、证据和程序结果的关键节点？
9. Discussion 如存在，是否明确区分现行义务和治理建议，并写出了具体制度缺口？
10. Sources 是否优先使用当前有效的一手 / 官方来源？
11. Takeaway 是否回到 Hero 的同一个判断或动作？
12. 页面是否仍只有一条阅读主线，没有因为“更完整”而重新变复杂？
13. 有没有一句话可以原封不动搬到另外 5 个 CASE？有就优先删除或具体化。
14. 有没有一句话删掉后，用户完全不少知道任何事实、判断或动作？有就删除。
15. 数字枚举是否真的帮助理解，而不是为了“四步 / 五类”的形式？
16. 比喻是否能一一对应到具体事实或结构？不能就删除。
17. 是否存在编辑者自言自语、口号式收尾、无证据情绪判断或不必要的绝对化建议？
18. 公共模板是否偷偷重新加入全站通用空话？

任何一项答不上来，就继续删、合并或重排。

最终标准：

> **用户每读一句，都应该多知道一个具体事实、判断或动作。组件可以统一，内容不能因为统一而失去信息。**

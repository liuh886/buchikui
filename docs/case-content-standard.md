# 不吃亏 / Buchikui — CASE Content Standard

> 状态：Normative  
> 适用范围：全部现有 CASE、新增 CASE、CASE 重写、消费者反馈吸收  
> 核心目标：**一个 CASE 只解决一个核心问题。先给判断，再解释关键原因，再告诉用户怎么做；法规只负责支撑判断和动作。**

## 1. 唯一主命题

每个 CASE 发布前必须先写出一句话：

> **这个 CASE 最希望用户下次改变哪一个选择或动作？**

这句话就是页面唯一主命题。Hero、立即行动、场景、处理路径、权利更新和 Takeaway 都必须服务于它。

如果一页同时在回答两个互不从属的问题，拆分 CASE；如果第二个问题只是例外、补救或已经出事后的处理，把它降到主线后半段，不与主命题并列。

禁止：

- 标题给一个结论，正文主要讲另一个问题；
- 同一结论换 3–4 种说法重复出现；
- 为了“完整”把多个法律维度并列成页面骨架；
- 用“四句话 / 五原则 / 六个法律问题”凑结构，而这些项目并不在同一层级。

## 2. 默认叙事顺序

所有 CASE 默认按下面顺序组织：

**结论 → 2–4 个关键理由 / 判断 → 现在怎么做 → 已经出事怎么办 → 法规与证据依据 → 最终经验**

### Hero

Hero 只做两件事：

1. 直接说核心判断；
2. 用 2–4 句解释为什么这件事与用户有关。

Hero 不讲法律史，不堆法规名称，不一次抛出多个抽象争议框架。

优先写：人、钱、授权、价格、主体、证据、时间、动作。

少写：责任结构、机制、链路、权利位置、闭环、治理框架等抽象词。

### 关键理由 / 判断

默认 3 项左右。每一项必须回答：

> **为什么这个核心判断成立？**

几个理由必须处在同一抽象层级，并且能够被用户直接比较、记住或执行。

例如“优先信用卡预授权”的三个理由可以是：

- 金额边界更清楚；
- 多一个独立争议入口；
- 交易证据更容易调取。

不能混成：产品机制 + 举证责任 + 平台责任 + 个案判决。

## 3. 法规只做支撑，不做目录

法规不是页面结构。先说消费者结论，再给依据。

一条法规进入默认阅读层，必须至少改变下面一项：

- 用户现在该做什么；
- 对方必须说明什么；
- 谁应当提供证据；
- 哪个授权 / 收费 / 履约行为有效；
- 责任或损失金额怎么判断；
- 投诉、申诉或诉讼应该找谁。

如果法规只能提供背景知识，留在 Sources，不进入主线。

同一问题优先保留最强法源：

1. 法律 / 行政法规 / 司法解释；
2. 部门规章 / 正式监管规则；
3. 指导性、典型或高价值生效裁判；
4. 平台 / 银行 / 商户协议用于说明具体业务机制；
5. 媒体和消费者反馈只用于发现问题，不作为法律结论。

普通个案只能说明“法院在这个事实组合下如何处理”，不能写成所有类似纠纷的普遍规则。

## 4. 只保留决定结果的关键点

一个事实或动作只有符合至少一项，才进入核心内容：

1. 会改变责任判断；
2. 会改变损失金额；
3. 会改变授权、收费或履约是否成立；
4. 会改变证据能否被取得、接受或核验；
5. 会改变投诉、调解、诉讼或执行结果；
6. 用户现在不做，以后很难补。

可以删：背景知识、常识提醒、重复流程、正确但不改变结果的说明。

不能删：主体、明确同意、授权范围、价格、损伤 / 服务前状态、时间、原始页面、交易记录、实际损失、关键期限等真正决定争议结果的节点。

核心纪律：

> **简化解释，不简化决定结果的过程。**

## 5. “已经出事”必须从选择逻辑中降一级

很多 CASE 同时包含“事前怎么选”和“出事后怎么救”。默认先帮助用户做下一次更好的选择。

如果用户已经进入纠纷，补救部分只保留 3–4 个动作：

**先固定什么 → 向谁要什么 → 哪两件事要分开判断 → 什么时候升级。**

不要让事后维权细节吞掉这个 CASE 原本的消费判断。

## 6. 场景只在确实改变判断时存在

Standard CASE 可以保留 Scenario-first，但每个场景仍必须服务于同一个主命题。

每个场景只保留：

### 关键事实

> 哪个事实真正改变责任、金额、授权或证据判断？

### 现在做什么

> 为了守住这个事实，我现在找谁、说什么、保存什么？

场景不是知识分类。两个场景如果动作和判断基本相同，就合并。

## 7. Immediate Actions

通常 3–4 项，只放跨场景最优先动作。

优先使用：

**对象 + 动作 + 要得到 / 保存的结果**

不要写“注意留证”“依法维权”“谨慎选择”这种没有操作结果的提示。

## 8. Evidence 与 Route

### Evidence

证据不是材料仓库。优先保留直接对应争议焦点的材料。

如果证据由商户、平台、银行或机构控制，明确告诉用户向谁索取，不默认全部由消费者自己寻找。

### Route

Route 只回答：

**什么时候升级 → 找谁 → 带什么 → 要什么结果**

普通办事流程放这里；决定输赢的事实留在前面的关键判断 / 场景里。

## 9. 当前权利更新

`legal-updates.js` 只展示会改变当前动作的最强规则。

它必须完成：

**新规则 / 新裁判 → 消费者多了什么权利 → 对方少了什么借口 → 现在具体可以要求什么。**

权利更新不能成为第二篇法规文章，也不能重复正文已经说清的核心逻辑。

## 10. Compact CASE

Compact CASE 默认结构：

**一句判断 → 约 3 个关键理由 / 条件 → 3–4 步动作 → 必要说明 → Sources → Takeaway**

不为形式统一补模块。

如果一个 Compact CASE 需要 6–10 个并列判断，先问是否应该拆分或改成 Standard CASE，而不是继续往页面上堆。

## 11. 语言纪律

Buchikui 的文字要像专业人士当面把事情讲清楚：短、准、具体。

默认顺序：

> **结论 → 关键事实 / 规则 → 动作**

要求：

- 三句能说完，不写五句；
- 一段只解决一件事；
- 法律名称放在消费者结论之后；
- 能说“谁扣了多少钱”，不要说“资金控制结构”；
- 能说“要求平台给出商户材料和审核依据”，不要说“推动证据流动”；
- “不是……而是……”不作为默认论证句式；
- 删掉正确但无用的句子。

## 12. Takeaway

每个 CASE 最后一条只回答：

> **下次重新做选择，最先改哪一步？**

只能有一句。它应该与 Hero 的主命题首尾一致，而不是在页面末尾突然提出新的价值判断。

## 13. 全部 CASE 的发布前验收

每次新增或修改 CASE，都必须逐项回答：

1. 我能不能用一句话说出这个 CASE 的唯一主命题？
2. Hero 是否直接支持这个主命题？
3. 默认可见的 2–4 个关键理由是否在同一层级？
4. 正文有没有突然转去讲另一个问题？
5. 是否有两个模块在重复同一结论？
6. 法规是否都在支撑判断或动作，而不是自己成为目录？
7. 是否保留了会改变责任、金额、授权、证据和程序结果的关键点？
8. 已经出事后的补救是否被放在主判断之后？
9. Sources 是否优先使用当前有效的一手 / 官方来源？
10. Takeaway 是否回到 Hero 的同一个选择？

任何一项答不上来，就继续删、合并或重排。

最终标准：

> **用户离开页面时只需要记住一个判断，并且知道为什么、下一步做什么、出了问题向谁要什么。**

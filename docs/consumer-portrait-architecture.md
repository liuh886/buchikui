# 消费者经历画像：架构与实施方案

日期：2026-10-24 · 状态：P0已按本方案本地实现，真实设备与用户验收待执行，未发布；见[开发交付记录](../tasks/consumer-portrait/delivery.md)。  
输入：[产品需求文档](consumer-portrait-prd.md)；执行：[实施计划](../tasks/consumer-portrait/implementation-plan.md)。

## 1. 架构结论

保留现有无运行时依赖的静态站、SQLite内容构建和独立本机回答库。新增确定性的浏览器画像与案例回报计算模块；角色、映射、短读内容均经版本化编辑输入及内容构建准入后发布。角色计算不依赖网络、服务器或运行时大模型。

首版结果分三层：角色与依据、两则具体案例回报、个人记录及范围明确的汇总。角色是经历主题表达；它不能测量稳定性格或消费能力。P0完成静态/本机版本，P1集中收卷另立设计，不借本机接口伪装上线能力。

本文为技术设计基线；首版本地代码、可重建内容数据库与资源已落地，云服务和线上发布未实施。

## 2. 必须收敛的产品边界

1. 当前八题按2/3/3分组。归一化比较是人为编排的主题映射，不是发生率、经验值或防骗能力。结果用“本次答卷的主题线索偏向……”及实际题项解释，不能用“你最容易在这里吃亏”。归一化最大组也不一定是YES绝对数量最多的组。
2. 画像门槛与统计有效完整答卷不是同一概念。走到末页但全skip可以看到小云朵与案例，不进入有效完整答卷汇总；8题都有记录且至少1题YES/NO可进入现有汇总，但若非skip不足6题，仍不能细分角色。
3. “初见小团雀”仅指本次未报告题面遭遇，不能解释为经验少、幸运、谨慎或新手。“留白”覆盖资料不足，不是负面等级。
4. 分享只在用户动作后生成本机图片或干净首页链接。角色名称本身会透露一个概括类别，所以预览应明确其将公开；不得在图片里追加实际遭遇、题数或标识。
5. 当前`shareUrl()`产生带`?question=`的中途入口，`survey-state.js.start()`会截取后半卷。画像版必须取消这种默认分享。历史题号深链直接从完整问卷首题进入，轻提示“从完整问卷开始生成角色”，另提供对应案例入口；不自动弹出案例，不把后半卷当整卷画像。既有`/c/<slug>/#rule-...`章节锚点保持不变。
6. P0保留NO/skip，不引入接触机会题，因此不输出“经历广度”“成熟度”等现有数据不能支持的维度。

## 4. 内容数据合同

新增配置采用以下逻辑结构，名称可按实现风格调整，语义必须保留：

```json
{
  "schema": 1,
  "rulesVersion": "portrait-1",
  "questionnaireVersion": "由构建计算",
  "minAnswered": 6,
  "minAnsweredPerGroup": 1,
  "groups": [
    {"id": "travel", "portraitId": "otter"},
    {"id": "prepaid", "portraitId": "capybara"},
    {"id": "after-sales", "portraitId": "raccoon"}
  ],
  "tiePortraitId": "fox",
  "noReportedPortraitId": "bird",
  "insufficientPortraitId": "cloud",
  "portraits": [
    {"id": "otter", "name": "旅途小海獭", "description": "泛化角色短句",
     "image": "角色发布资源键", "thumbnail": "缩略图资源键", "alt": "插画替代文字"}
  ],
  "lessons": [
    {"id": "tour-museum-lesson", "questionId": "survey-tour-museum",
     "caseId": "case-consumer-tour-museum", "topicSlug": "travel-booking",
     "ruleId": "consumer-tour-museum", "priority": 10, "introPriority": 10,
     "situation": "发生了什么的审核短句", "outcome": "原案处理结果短句",
     "boundary": "必须保留的适用边界", "notice": "下次值得留意的具体事实"}
  ]
}
```

示例数组为结构演示，构建要求实际六角色齐全、三组齐全。`questionnaireVersion`不由编辑手填，构建时由按固定顺序的`[questionId, questionVersion, groupId]`集合计算。题量变动时必须重审规则门槛，不能把“6”偷偷按新题数缩放。

公共内容升级为schema 3，增加`questionnaireVersion`和`portrait`。画像配置入内容数据库后再投影到`content-data.js`，本机API与离线快照共用同一投影。载荷包含审核短读和来源投影，不包含审核人、讨论、未发布角色、未核验案例或设计源文件。

`lessons`是原案的审核短读，不是新的来源登记。`caseId`必须是对应规则的直接支撑案例，且仍为verified/eligible；出处标题、机关、日期、核验日、URL从既有来源投影生成，禁止编辑重复URL。原案事实/结果/边界或规则实质改变时，构建使短读审核指纹失效，要求重审，不能继续复用过期短句。

因此每则短读另存内部`reviewedAgainst`哈希：绑定案例facts/holding/boundary、规则text/action及对应来源的效力/核验相关字段。构建重算不一致即阻止发布。语法/字段校验不能替代内容审核；`notice`仍需编辑确认不超出原案与规则边界。

## 5. 画像计算

输入只接受当前完整卷的问题ID和语义版本匹配的响应。纯函数输出：`status`、`portraitId`、`rulesVersion`、`questionnaireVersion`、`reasonQuestionIds`、`answeredCount`、`skippedCount`；不输出能力分或百分位。

1. 必须已走到整卷末页，且每题恰有一条yes/no/skip响应；未走完只返回`in-progress`，不展示最终角色。
2. 非skip少于6或任一组非skip为0：`insufficient/cloud`。保留真实YES记录用于个人记录；可提供案例，不强行给主题结论。
3. 满足覆盖且总YES=0：`no-reported/bird`。文案为“这次列出的遭遇，你还没有报告过”；有skip时补充“另有n题暂未回答”，不得写“全都没有过”。
4. 其余计算每组`yesCount/groupQuestionCount`。固定分母是整卷该组题数，不能用已答题数；这是主题映射，不展示为风险比例。
5. 两组a/b用整数交叉相乘比较`yesA * totalB`与`yesB * totalA`，不以浮点四舍五入判并列。最大值唯一取组角色；最大值并列且大于0取fox。
6. 取对应组实际YES问题作为理由；fox取并列组的YES题项。理由先明确“按这份问卷的主题规则生成”，再列具体记录。用户修改时仅使用当前`state.responses`重算，不从历史`data.records`拼接已撤回的答案。

例：旅游1/2、预付1/3、售后0/3→海獭。旅游0/2、预付1/3、售后1/3→狐狸。旅游2/2、预付3/3、售后3/3→狐狸。旅游1/2、预付2/3、售后0/3→水豚，理由不能声称水豚组拥有多数全部经历。NO与skip不会被用来奖励成熟度。

跳过可能改变映射，结果需明示其数量。首版不自动随机分角色、不按用户喜好重新抽取。角色名称与插画经理解测试调整，但角色ID稳定。

## 6. 两则案例回报选择

候选由审核后的`lessons`构成，不运行全文检索或自由生成。每题至少一个可发布候选；至少两个不同组的候选具有明确`introPriority`，保障无YES也有回报。

对每次整卷结果：

1. YES对应的候选按`priority`、问卷顺序、lessonId稳定排序。优先每主题取一则，避免两张停业卡讲同一件事；若YES只有一个主题，先取一则该主题的匹配案例。
2. 不足两则时按`introPriority`、问卷顺序、lessonId，从尚未选择主题的入门候选补足。若所有可用候选只在同主题，宁可只展示一则并记录内容缺口；标准发布门禁要求至少两个主题可用，不能用重复卡凑数。
3. 对caseId和`[topicSlug, ruleId]`分别去重，同一原案或同一规则不重复成两则。
4. 即使画像覆盖不足，有YES时也可显示匹配案例，但只表述“你勾选的这件事有一则原案可参考”，不生成完整画像理由。全NO、全skip均走入门候选，标题区分未报告与未回答。
5. 首层至少包含situation/outcome/boundary/notice与原文入口。折叠不能把决定结论的边界藏到第二层。展开详情直接复用当前`q.analysis.cases`的事实投影。

配置变更仅改变推荐版本或内容revision，不修改原有回答。新快照撤下某候选后不从旧缓存混补该候选。若发布配置损坏，画像降级为可读个人记录和资料库入口，不阻止既有回答保存。

## 7. 版本、迁移与缓存

| 版本 | 改变条件 | 对回答与结果的影响 |
| --- | --- | --- |
| question.version | 问句语义/决策分类改变 | 沿用既有语义隔离；旧回答保留，不混入新版 |
| questionnaireVersion | 题目成员、语义版本、分组或固定顺序改变 | 重审画像；提示卷已更新；旧完整答卷不被静默解释为新版画像 |
| portrait.rulesVersion | 门槛、主题映射、分配逻辑改变 | 明示“画像规则已更新”，依据当前完整响应重算，不改答案 |
| lesson审核指纹/内容revision | 原案、规则、短读或角色展示内容改变 | 重审短读，刷新快照；单纯插画/文案修正不要求重新答题 |
| 资源内容哈希 | 插画字节改变 | 新URL与新SW清单，避免旧图对应新角色文案 |

存储外层继续保留现有随机ID、sequence、records、pending，不删除或重置已收响应。`state`升级schema 3，新增`questionnaireVersion`与`portraitRulesSeen`，保留旧schema 2适配器。

schema 2若为当前完整固定顺序，按版本逐题验证后迁移；未完成可保留前缀；遇变更从最早变更位置继续。原有中途深链截断状态不认作完整卷：保留records/pending，在通知后从整卷首题进入，旧历史不擅自拼成一次完整会话。统计接口现有按当前版本全量问题判完整的逻辑保持；P1若需要严格每次会话统计，应另设计会话标识与迁移，不在此伪称已经做到。

`installContent()`必须原子校验并替换questions、journeys、portrait及版本；失败整体保留旧快照。不能先更新问题再留下旧角色规则。仅接受schema 3完整发布包；代码与数据不兼容时保留清晰重载/资料库后备，不能悄悄误分类。

SW更新包括新脚本与所有发布角色全图；缩略图可按需缓存。构建从同一资源清单注入SW的带标记数组段，并校验注入防漂移；不手抄六份路径。`cache.addAll`失败不得使新缓存部分安装被当作成功；旧可用版本继续运行。仅清理`buchikui-pwa-`缓存。网络数据与旧缓存版本在原子内容校验下使用，避免混合规则。

## 8. 视觉资源、导出与降级

每角色交付512×512透明WebP全图和128×128缩略图，建议预算分别≤60KiB、≤12KiB；六角色共≤432KiB。预算是本版验收目标，不声称当前已有素材。原始高分辨率画稿不进入发布物。每个文件用内容哈希命名，由构建复制到`portraits/`并生成资源表；不得接受跨域图片路径。

首屏问卷不请求角色全图；结果只渲染对应全图。布局保留固有宽高避免跳动。图片失败显示同面积的角色文字与简约替代图形，仍有名称/理由/案例。文字不能依赖插画或颜色才能理解。

分享P0采用浏览器Canvas固定模板，不引入DOM截图依赖或远程渲染：同源图片`decode()`→系统字体就绪→显式逐行布局→`toBlob('image/png')`。竖版1080×1440为导出画布，预览按CSS缩放；字段限定为公共角色模板，函数参数不接收responses/participantId。

中文按字素或可迭代码点进行测量换行，名称/短句有长度上限；图片可用时显示插画，失败可导出名称版，预览明确反映实际输出。Canvas错误不能影响问卷或个人结果。

点击“生成角色卡”只生成预览，不自动下载或唤起分享；“保存图片”下载Blob，设备不支持下载时提供可打开的大图与长按保存提示；“系统分享”在`navigator.canShare({files})`支持时传File，取消静默返回。其他情况保留保存图片及干净问卷链接复制。不使用动态公开结果页、不上传图片、不推送消息。

对象URL在关闭预览/替换卡片后回收；预览与生成中的按钮有状态和读屏反馈。浏览器API通过特性检测降级，不能凭桌面可用断言iOS/Android分享可用，需真实设备验收。

## 9. P0/P1部署与数据边界

P0沿用GitHub Pages静态产物，本地依旧可运行受限接口。画像、短读、导出全在客户端完成；没有服务端也能完整兑现个人回报。只有本机localhost会同步现有survey接口，不扩大现有网络信任边界。

P1需单独决策：托管方案、接口域/HTTPS/CORS、匿名写入防滥用、保留/删除策略、备份恢复、问卷版本分区、样本口径与运维。现有Origin校验只适用于本机HTTP，不能原样复制到生产。Supabase原product_feedback不是答卷表；选用该服务前须按其专项规范另评审。费用与服务版本未在本方案核查，不预作已验证选型。

P0不新增产品行为上报；理解测试通过经同意的观察记录完成。P1指标必须区分到达末页、统计有效完整答卷、画像可细分；没有事件采集不能凭页面功能宣称完成率或分享送达率。

## 11. 架构评审建议回写PRD

- 明确归一化主题不等于YES绝对数量最多，理由避免“这类最多”误导。
- 解释无YES但存在skip不能叫“全NO”；画像覆盖与统计完整条件分开。

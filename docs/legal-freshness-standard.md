# 不吃亏 / Buchikui — Legal Freshness Standard

> 状态：Normative  
> 适用范围：全部 CASE、消费者反馈吸收、法律 / 监管 / 平台规则更新  
> 核心目标：**不做法律新闻，不做法条百科；只把真正改变消费者位置的新规则，翻译成今天可以执行的动作。**

## 1. Buchikui 的普法是什么

Buchikui 的普法不是“告诉用户有一部新法”。

每条法律更新必须完成这次翻译：

**新规则 / 新裁判 → 消费者多了什么权利 → 对方少了什么借口 → 现在可以要求什么 → 哪份证据必须马上保存。**

如果一项新信息不能改变用户的判断、证据、责任位置、损失金额或升级路径，就不要进入默认阅读主线。

## 2. 每个 CASE 都是 Living Case

每个 CASE 都应被视为有“法律版本”的行动指南，而不是一次写完的文章。

公开页通过 `legal-updates.js` 展示每个 CASE 当前最值得用户知道的一个权利变化 / 监管抓手，并标注最近核验日期。

默认只显示 **1 个最强更新**。不要把 CASE 变成法规时间线。

## 3. 法律新鲜度检查

新增 CASE、重写 CASE、吸收消费者反馈时，除现有 CASE Content Standard 外，必须检查：

1. 当前有效的法律、行政法规、司法解释、部门规章；
2. 最近两年是否有直接相关的新规、修订、监管规则或正式监管口径；
3. 最近两年最高人民法院是否发布相关指导性 / 典型案例；
4. 是否有能够揭示现实争议结构的生效裁判；
5. 平台、银行、支付机构、运营商等自己的现行协议 / 规则是否已经变化。

发现新材料后先问：

> **它有没有让消费者现在“可以多要求一件事”，或者让经营者“不能再用某个理由推脱”？**

有，进入 CASE；没有，只留在研究依据，不占页面。

## 4. 来源权重必须说清

Buchikui 不笼统使用“判例证明了”。至少区分：

- **法律 / 行政法规 / 司法解释**：可以直接用于说明规范性权利义务；
- **部门规章 / 监管规则**：在其适用范围内用于说明经营、销售、投诉、平台治理等具体义务；
- **指导性案例**：用于说明类似案件的重要裁判规则和裁判方法；
- **最高法典型案例 / 人民法院案例库入库案例**：高价值裁判参考，但不得写成所有法院必然作同一结论；
- **普通生效裁判**：用于证明“真实争议已经发生、法院曾如何处理”，不得直接泛化为全国统一规则；
- **媒体调查 / 消费者反馈**：用于发现问题模式，不得单独作为法律规则依据；
- **平台 / 商户协议**：只能证明合同如何设计和当事人如何自我定位，不能用来替代法定义务。

用户可见来源标题优先加 `【司法解释】`、`【部门规章】`、`【监管典型案例】` 等权重提示。

## 5. 最有价值的写法

优先把规则改写成消费者可以直接使用的判断和请求。

### 不要这样写

> 《网络交易平台规则监督管理办法》第十九条规定平台应建立申诉机制。

### 应该这样写

> 平台不能只回复“系统判定”。它依据平台规则对你作出不利处理时，应说明事实、理由和依据；你要求人工判定时，不能只交给 AI / 系统处理。

然后给出动作：

> **要求平台提供：具体规则条款 + 对方提交材料 + 平台审核依据 + 人工复核结果。**

这就是 Buchikui 的普法标准。

## 6. 五种优先进入 CASE 的法律变化

新信息出现时，优先保留这五类：

1. **举证责任变化**：谁控制证据、谁应提交、拒不提交会有什么后果；
2. **平台 / 中介责任变化**：不能再简单推回商户、第三方或“系统”；
3. **格式条款 / 授权边界变化**：默认同意、自动续费、持续扣款、免责、争议处理；
4. **投诉 / 申诉程序变化**：必须答复、人工复核、调单、监管受理条件和期限；
5. **损失 / 退款 / 责任计算变化**：什么可以退、怎么计算、谁证明金额。

普通政策背景、行业宣传、与用户动作无关的宏观信息，不进入主线。

## 7. 对“新判例”的纪律

判决最容易被过度使用。

每次引用裁判都要分清三件事：

1. **法院实际认定了什么事实；**
2. **法院在该案中适用了什么规则；**
3. **Buchikui 从这个争议中提炼出的操作提醒是什么。**

三者不得写成同一种确定性。

禁止：

- “法院已经规定……”（如果只是普通个案）；
- “这种情况一定能退 / 一定能赢”；
- 用一个地方判决替代当前有效法规；
- 只摘消费者胜诉部分，不写决定结果的事实条件。

## 8. 平台协议不是法律终点

当平台、支付机构、银行、运营商通过协议把自己描述为“技术服务方”“信息服务方”“支付通道”“仅执行指令”时：

1. 先准确说明该合同定位；
2. 再检查法律、行政法规、部门规章是否仍给它配置平台治理、支付安全、投诉处理、适当性、信息提供或证据保存义务；
3. 不接受“协议写了不负责 = 法律上没有责任”的推理。

**合同可以分工，不能当然消灭法定义务。**

## 9. 更新方式：替换，不堆叠

新规进入后：

- 优先替换旧的弱表达；
- 删除已经过时的口径；
- 同一权利只解释一次；
- `legal-updates.js` 只保留当前最强的一条更新；
- CASE Sources 可以保留更完整依据。

不要不断 append “2024 新规 / 2025 新规 / 2026 新规”，让页面变成历史档案。

## 10. 发布前 Legal QA

每次 CASE 内容变更最后检查：

1. 当前引用的规则是否仍有效；
2. 是否优先使用官方 / 一手来源；
3. 是否把裁判权重说对；
4. 是否把新规则翻译成了用户动作，而不是法条摘抄；
5. 是否出现“必然胜诉、必然退款、平台当然无责 / 有责”等过度结论；
6. 是否更新 `legal-updates.js` 中对应 CASE 的权利核验；
7. 新内容是否让页面更有行动价值，而不是单纯更长。

最终标准只有一句：

> **用户读完以后，不只是“知道法律变了”，而是知道下一句话该怎么说、下一份证据该向谁要。**

# 不吃亏 / Buchikui — Legal Freshness Standard

> 状态：Normative  
> 适用范围：全部 CASE、消费者反馈吸收、法律 / 监管 / 平台规则更新  
> 核心目标：**不做法律新闻，不做法条百科；只把真正改变消费者判断和动作的规则，翻译成今天可以直接使用的权利抓手。**

## 1. Buchikui 的普法是什么

每条法律信息必须完成这次翻译：

**规则 / 裁判 → 这件事真正争什么 → 消费者多了什么权利 → 对方少了什么借口 → 现在可以要求什么。**

如果一项信息不能改变用户的判断、证据、责任位置、损失金额或升级路径，就不进入默认阅读层。

法规服务于消费问题，不反过来组织 CASE。

## 2. 权威依据层的唯一用途

`legal-updates.js` 是权威材料层的唯一数据源，页面上呈现为 **权威依据 / 裁判参考**。

它只回答：

> **这个场景背后，当前最重要的规则给了我什么抓手？**

内部曾用“权利校验”称呼这一层，那是实现代号；**用户可见名称只有“权威依据”和“裁判参考”两个**，
不要把 Rights Check / Rights Pulse 一类内部术语写进读者可见文案。

### 单条还是 Tabs

- 只有一个真正关键的权利问题时，只展示一条；
- 只有存在 **2–4 个彼此独立、都足以改变消费者动作的权利问题** 时，才使用 Tabs；
- 不为视觉统一凑 Tab；少一项比塞入一项边缘法规更好；
- 默认最多 4 项，按当前消费决策的重要性排序。

### Tab 准入门槛

一个关键词只有同时满足以下条件，才可以成为 Tab：

1. **切题**：直接对应本 CASE 中高频、真实、会造成损失的消费问题；
2. **重要**：会改变消费者现在的选择、留证、付款、签字、投诉、申诉或诉讼动作；
3. **独立**：和其他 Tab 不是同一权利的换一种说法；
4. **有硬依据**：优先有现行法律、行政法规、司法解释、部门规章或正式监管规则直接支撑；
5. **能落到一句动作**：必须能写出“你现在可以要求 / 现在应当做什么”；
6. **当前有效**：已核对效力、实施日期和适用范围。即将生效的规则必须明确标注日期，不能写成当前权利。

任一条件不满足，就只留在 Sources 或研究依据，不进 Tab。

**媒体与网络爆料不能单独作依据。** 网传帖、论坛、Reddit、自媒体报道最多只能用于*发现*问题；
要么找到一手法源并改写为规则，要么整条删除，不得以 `type: 网络爆料` 之类的标签留在 Tab 里。
已确认的执法案件、监管通报可以进 Tab，但必须写明制度地位（`type`）并给出可打开的通报链接；
媒体转载官方通报时，标题要写成「【警方通报·某媒体报道】」而不是「【官方通报】」。

### Tab 怎么命名

Tab 名必须是 **消费者问题关键词**，不是法规名、机关名或年份：

- 好：`维修行为 / 明码标价 / 搜索广告 / 投诉举报`
- 好：`风险测评 / 收益宣传 / 产品匹配`
- 好：`调单核查 / 授权举证 / 平台申诉`
- 不好：`当前规则 / 即将生效 / 2026新规 / 司法解释`

`现行 / 即将生效`、规则类型、发布机关、实施日期属于 Tab 内 metadata，不占用问题关键词。

## 3. 每个 Tab 必须包含什么

每项只保留：

1. **问题关键词**；
2. **状态**：现行 / 即将生效；
3. **法源类型与发布机关**；
4. **实施日期**；
5. **规则名称**；
6. **一句消费者判断**；
7. **一段必要解释**；
8. **一个具体动作**；
9. **官方 / 一手原文入口**；
10. **最近核验日期**。

一个 Tab 最好由 1 个最强法源支撑；确实需要两项规则共同完成同一个判断时，可以放 2 个来源。不要把 Sources 全搬进权威依据层。

### 3.1 来源链接的纪律

- 指向**文件本身**，不是机构首页：`https://www.gov.cn/...` 合格，`https://weibo.com/` 不合格。
  契约脚本会拒绝权威层里路径为空的链接。
- 一手优先：法律、行政法规、司法解释、部门规章、监管文件走发布机关官网或公报。
- 只能拿到媒体转载时，链接仍是那条报道，标题如实标注「【…·某媒体】」；
  不要因为内容来自官方就把媒体链接写成「官方原文」。
- 办事入口（12315、12345、网上立案平台、运营商网上营业厅）不是法源，
  放在 CASE 的 `sources` 里并写成「入口 / 平台」，不要混进权威依据 Tab。

### 3.2 核验日期的纪律

每条依据的 `verified` 字段是**这一条**被复核的日期，页面上显示为「核验 YYYY-MM-DD」。
没有单独 `verified` 的依据退回模块级 `VERIFIED`，显示为「本批核验 YYYY-MM-DD」——
这是一个诚实的降级说法，不是「这一条也核验过」。

- 新增或修改任何一条依据时，必须同时写 `verified`；
- 只有整批依据统一复核时才更新模块级 `VERIFIED`；
- 「原文」段显示的核验日期取本主题所有 `verified` 的最大值，没有则为 0（不显示）。

## 4. 法律新鲜度检查

新增 CASE、修改 CASE、吸收反馈或更新权威依据时，必须检查：

1. 当前有效的法律、行政法规、司法解释、部门规章；
2. 最近两年是否有直接相关的新规、修订或正式监管口径；
3. 最近两年最高人民法院是否发布相关指导性 / 典型案例；
4. 是否存在能够揭示现实争议结构的高价值生效裁判；
5. 平台、银行、支付机构、运营商等自己的现行协议 / 规则是否变化。

发现材料后先问：

> **它有没有让消费者现在多要求一件事，或者让经营者少一个推脱理由？**

没有，就不进入权威依据层。

## 5. 来源权重

至少区分：

- **法律 / 行政法规 / 司法解释**：可直接说明规范性权利义务；
- **部门规章 / 正式监管规则**：在适用范围内说明具体经营、销售、投诉、平台治理等义务；
- **指导性案例**：说明重要裁判规则和方法；
- **最高法典型案例 / 人民法院案例库入库案例**：高价值参考，不写成所有案件必然如此；
- **普通生效裁判**：证明现实争议和个案处理，不泛化成全国统一规则；
- **平台 / 银行 / 商户协议**：说明合同机制和主体自我定位，不能替代法定义务；
- **媒体 / 消费者反馈**：只用于发现问题，不单独作为权利依据。

用户可见来源标题优先带 `【司法解释】`、`【部门规章】`、`【行政法规】` 等权重提示。

## 6. 写法：先说权利，再说法条

不要写：

> 《网络交易平台规则监督管理办法》第十九条规定平台应建立申诉机制。

应该写：

> **平台不能只回复“系统判定”。** 它依据平台规则对你作出不利处理时，应说明事实、理由和依据；你要求人工判定时，不能只交给系统。

动作：

> **要求平台提供：具体规则条款 + 对方提交材料 + 审核依据 + 人工复核结果。**

法律名称放在 metadata 和来源里，不抢消费者判断的位置。

## 7. 最值得进入权威依据的五类问题

优先考虑：

1. **举证责任**：证据在谁手里、谁应提交、拒不提交的后果；
2. **平台 / 中介责任**：不能简单推回商户、第三方或“系统”；
3. **授权 / 同意 / 格式条款**：持续扣款、默认同意、免责、单方变更；
4. **投诉 / 申诉程序**：答复、人工复核、调单、受理条件和期限；
5. **退款 / 收费 / 损失计算**：什么能退、什么能收、金额如何证明。

普通行业背景、政策愿景、宏观整治口号和不会改变用户动作的知识，不进入 Tab。

## 8. 裁判与平台协议纪律

引用裁判时必须分清：

1. 法院实际认定的事实；
2. 法院适用的规则；
3. Buchikui 提炼的操作提醒。

普通个案不得写成“法院已经规定这种情况一定能退 / 一定能赢”。

平台、支付机构或银行把自己描述为“技术服务方”“支付通道”“仅执行指令”时，先准确说明合同定位，再检查法律是否仍配置平台治理、支付安全、投诉处理、适当性、信息提供或证据保存义务。

**合同可以分工，不能当然消灭法定义务。**

## 9. 更新方式：替换，不堆叠

- 新规则优先替换旧弱表达；
- 已过时口径直接删除；
- 同一权利只解释一次；
- 单条足够时绝不升级成 Tabs；
- 多规则时按问题关键词组织，不按年份组织；
- 即将生效的规则如果属于一个新的、重要的消费者问题，可以独立成 Tab；如果只是同一问题的新版本，优先在同一问题下说明时间边界；
- CASE Sources 保留更完整依据，权威依据层只留最强依据。

## 10. 发布前 Legal QA

每次变更最后逐项问：

1. 这条规则现在有效吗？
2. 这是官方 / 一手来源吗？链接能不能直接打开到那份文件，而不是机构首页？
3. 如果链接是媒体转载，标题有没有如实标注媒体报道？
4. 这个关键词真的属于本 CASE 的高频关键问题吗？
5. 删除这个 Tab 会不会让消费者做错一个重要动作？如果不会，删掉；
6. 它与其他 Tab 是否重复？
7. 裁判权重有没有说对？（监管通报不是裁判，媒体爆料不是依据）
8. 是否明确区分现行与即将生效？
9. 用户能否从这条规则直接得到一句可执行请求？
10. 权威依据层是否比修改前更短、更准，而不是更全？
11. 改动的这一条写 `verified` 了吗？

最终标准：

> **只展示最切题、最重要、最能改变行动的规则。用户看完不仅知道“有法律”，还知道下一句话怎么说、下一份证据向谁要。**

## 11. 复核节奏

法律不会自己更新，站点也不会自动提醒，所以节奏必须写下来：

| 周期 | 动作 |
| --- | --- |
| 每条依据改动时 | 立刻写该条的 `verified` |
| 每 90 天 | 复核本主题全部依据的效力状态与来源可达性，并写 `verified` |
| 每 180 天 | 按 §4 重新扫一遍近两年新规、修订、监管口径与典型案例 |
| 每年 | 复核「原文」段里所有办事入口链接是否仍然有效 |

`node scripts/check-frontend-contract.mjs` 会在结尾打印每个主题的核验覆盖情况
（`N/16 topics carry a per-rule verified date`）。它**不判定过期**，只暴露覆盖度：
覆盖度长期偏低说明 §3.2 的纪律被绕过了，应先补日期，再谈内容更新。

## 1. 产品定义

“不吃亏”是一个**消费普法 + 决策指南**平台。

它不替用户做 AI 式纠纷诊断，不提供维权工具箱，也不做法条百科。它从公开、可核验的权威材料里
提取现实交易中最容易忽视、但会改变结果的关键点，然后让读者在**真实情景里做出选择**。

核心链路只有一条：

> 现实交易情景 → 权威依据 → 关键事实 → 现实提醒。

产品的第一交互不是检索，而是**判断**：给出一个具体情景和几个选项，读者先选，再看正解与依据。
资料库没有消失，它从首页移到了导航和目录里，并且被重新组织成一本可以顺序读的书。

## 2. 首页：一张情景卡

### 2.1 首屏结构

```text
导航 bar（随机情景 / 搜索主题 / 目录 / 反馈入口）
──────────────────────────────────────
情景卡（主界面，居中，最大视觉权重）
  题面：≤ 80 字
  选项：单选或复选，≤ 18 字/项
  ─────────────────────────────────────
  三个小按钮 + 一个反馈按钮
──────────────────────────────────────
（首屏之下）按主题挑 → 全部主题列表 + 筛选
```

首屏必须同时可见：品牌与一句定位、情景卡、以及卡上的按钮。**不使用弹窗**：
弹窗同时踩三条线——首屏规范、390px 无溢出、无障碍焦点陷阱。

### 2.2 题目数据结构

新增 `scenario-checks.js`，每题：

```js
{
  id: 'lodging-cancel',
  type: 'single',                 // single | multi
  situation: '民宿订单已确认，房东来电说水管爆了，请你取消。',
  options: [
    { id: 'a', text: '在 App 里按“主动取消”提交，拿全额退款' },
    { id: 'b', text: '同意取消，但要求平台补一张券' },
    { id: 'c', text: '不主动取消，要求房东在平台内发起取消并写明理由' }
  ],
  answer: ['c'],                  // 单选恰好 1 项；多选 ≥ 2 项
  why: '主动取消会被记为用户违约，通常无法主张违约责任；房东违约应由其在平台内发起取消。',
  ruleId: 'lodging-breach',       // 必填，指向 legal-updates.js 的 id
  caseSlug: 'qingdao-travel',
  now: '截图订单确认，要求房东在平台系统内取消并写明原因，同时提出替代房源差价主张。',
  exception: '若平台规则提前明确标注不可抗力可免费取消，以平台规则为准。'  // 必填
}
```

**答案只能来自 `legal-updates.js` 已有的依据**，不得为题目另立一套说法。题目是同一批权威材料的
另一种呈现，不是第二份真相源。

### 2.3 卡片状态机

```text
未答 ──选择──> 已判定 ──点击卡片 / 查看答案──> 已翻面 ──下一题──> 未答（新卡）
  │                                                  ▲
  └──跳过（直接翻面，不判定）───────────────────────┘
```

- 单选：**不需要提交按钮**，点选即判定；
- 多选：点选即标记，选满「提交」按钮出现后才判定（多选不能一选就知对错）；
- 翻面 = 同一张卡内从正面切到背面，**不做 3D 旋转**；`prefers-reduced-motion` 下同样工作。

### 2.4 判定

- 选完立刻显示正解：**正确项标红并标「正解」**；
- 读者选错的项做灰化处理，不用叉号、不用“你错了”；
- 结果用 `aria-live="polite"` 播报「正解是 C」；
- 判定的唯一目的是让依据被看见，不是给读者评分。

### 2.5 翻面后的解析

固定四段，顺序不可变，总长 ≤ 150 字：

1. **正解**：一句话；
2. **依据**：一条，锚到该 CASE 的 `#rule-<ruleId>`；
3. **现在做什么**：一句，具体到“说哪三句话”或“要哪个编号”；
4. **什么时候不适用**：一句。

第四段不可省。真实交易有例外，只给唯一正解而不写例外，会让读者照做而吃亏——
这是本项目最不能犯的错。

### 2.6 随机

- 打开首页随机出一题；
- 「换一题」在题库内随机；
- 随机的是**情景**，不是随机推荐 CASE 页；每张卡背后仍然是一个固定地址的固定章节。

### 2.7 卡片上的四个小按钮

| 按钮 | 行为 | 落点 |
| --- | --- | --- |
| 跳过 | 不判定，直接翻面看解析 | — |
| 换一题 | 换一张随机卡 | — |
| 查看答案 | 翻面看解析（已判定时用于回看） | — |
| 这题有问题 | 打开预填标题的 GitHub issue | 仓库 issue |

四个按钮视觉权重必须低于选项，避免被当成主要操作。

### 2.8 题目反馈

「这题有问题」是**对仓库内容的纠错**，走 GitHub issue（预填题号与选项），不带入消费者经历队列。
消费者亲历与信息纠错仍走 `docs/consumer-feedback.md` 定义的 Supabase `product_feedback` 管线。
两者是不同的对象，不进同一个队列，也不互相当作对方的入口。

## 3. 导航

首页之上是一条常驻导航：

- **随机情景**：回到情景卡；
- **搜索主题**：进入可检索的主题资料库（保留现有多维筛选与关键词搜索）；
- **目录**：进入电子书式目录；
- **反馈入口**：指向仓库 issue。

导航是资料库与决策卡之间的唯一通道。不要在导航里放 Dashboard 指标、完成度或推荐位。

## 4. 目录：一本书的目录

- 目录页把全部主题按**卷 / 章**编排，而不是按平行分类平铺；
- 每章一行：卷号、章序、现实问题一句话、依据类型、最近更新；
- 目录同时是内容索引、阅读路径与对外的可读目录；它由数据生成，不手写；
- 初始卷序（待确认）：

| 卷 | 主题 |
| --- | --- |
| 一、把钱要回来 | 租车 · 信用卡预授权 · 预付消费 · 小额账户费 · 银行理财 · 投顾费用 · 拍卖 |
| 二、平台与商家 | 套餐 · 家电维修 · 机场推销 · 网约车与货运 · 出租 |
| 三、人生转折 | 被裁与补偿 · 相亲安全 · 恋爱与个人财产 |
| 四、远行与境外 | 泰国旅行 · 青岛旅游 |
| 五、自己去打 | 第一次自己打民事官司 |

卷序只表达**阅读先后**，不表达重要性，也不参与筛选维度。

## 5. CASE = 书的一章

### 5.1 地址

`/c/<slug>/` 继续是唯一规范地址。形态改成书的一章：顶部有目录入口与章序，
底部有上一章 / 下一章，页面本身仍是这一章的完整正文。

合并不删除地址。理由：canonical、sitemap、预渲染正文、结构化数据与已被分享的链接都已经存在，
删除它们等于一次性丢掉搜索与分享资产，而“像书一样读”并不需要这个代价。

### 5.2 章内结构

> 现实问题 → 权威依据 → 现实交易提醒 → 证据与处理路径（按需） → 原文 → 一句可迁移经验

章序以中文数字 + 题目呈现（如「第三章 · 家电维修」）。
**章序与内部 id（`001`、`002`）是两件事**：章序是给读者看的编排，internal id 不进入任何用户可见位置。

### 5.3 首章

打开任意一章时，页面必须能让读者立刻回答：这一章在讲什么现实问题、答案在第几节。

## 6. 题目纪律

判对错是这个产品里风险最高的交互，因此以下为硬约束：

1. **每题必须挂 `ruleId`**，答案必须是 `legal-updates.js` 里现行有效的依据；
2. **每题必须写 `exception`**，写清什么时候不适用；
3. **以单选为主**，只在同一问题存在多条正解时才出多选；多选题不得靠排除法就能做对；
4. **题目随依据复核**：依据的 `verified` 变更时，同步复核该题；
5. **禁止题型**：与真实交易无关的常识题、靠记忆年代或数字的选择题、把法条原文当选项的题、
   选项之间表述不平行（一个含具体金额、一个不含）的题；
6. **禁止语汇**：维权神器、必胜、避坑、教你一招、千万注意、否则血本无归；
7. 题量宁少勿滥：**首批 12–15 题**，每题对应一个高杠杆情景。

## 7. 权威依据

用户可见名称统一使用：

- **权威依据**：法律、行政法规、司法解释、部门规章、监管文件、监管通报等；
- **裁判参考**：指导案例、典型案例、监管处罚案例、普通裁判等。

必须明确：来源类型、机关 / 法院、文件 / 案号、生效或裁判时间（如有）、核验日期、原文链接。
媒体转载官方通报时，标题如实标注为媒体报道，不得写成官方原文。
Buchikui 的解释不能伪装成法条原文；普通裁判不能被写成普遍法律规则。

## 8. 视觉语言

页面应像一个可信的编辑型普法资料库：纸张感、强排版、少卡片、少按钮、少状态 UI。

本次修订允许**一处例外**：情景卡可以是卡片形态（它是一次性互动界面）。
但除情景卡外，仍以标题、细线、列表、文献式元信息为主。

避免：大面积彩色卡片、发光按钮、仪表盘、数字进度、成就、连续天数、排行榜、AI 助手口吻。

**允许的“考试感”**：题面、选项、判定红标、正解标记、翻面。
**禁止的游戏化**：分数、等级、进度条、成就徽章、连续天数、排行榜、分享得分。

## 9. 移动端

390 px 宽度必须：

- 无横向溢出；
- 首屏可见品牌定位、情景卡与卡上按钮；
- 情景卡在窄屏上按「题面 → 选项 → 按钮」纵向堆叠，不横向排布选项；
- 选项触摸目标 ≥ 44px；
- 卡片上四个小按钮触摸目标 ≥ 44px 但视觉上保持弱化；
- 权威依据允许纵向堆叠；
- 无固定底部双 CTA。

## 10. Definition of Done

发布前检查：

1. 打开首页是否立刻出现一张情景卡，且不需要任何操作；
2. 选完是否立刻看到正解红标，且不需要提交；
3. 每题是否都挂到现行依据，每题是否都写了什么时候不适用；
4. 翻面解析是否四段齐全、≤ 150 字、没有营销词；
5. 四个小按钮语义是否不重叠、是否都比选项弱；
6. 导航能否到达搜索、目录、反馈；
7. 目录是否按卷章编排，且由数据生成；
8. CASE 是否仍是固定地址的独立章节；
9. 页面里是否出现分数、进度、成就或排行榜；
10. 有没有仍然像“AI 给我做诊断”的模块？有则删除；
11. 权威依据与 Buchikui 的现实翻译是否仍清楚分离；
12. 原文能否直接打开；
13. `node scripts/check-frontend-contract.mjs` 是否通过。

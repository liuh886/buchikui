# 不吃亏 / Buchikui — Product Experience SPECS

> 版本：v1.1  
> 状态：Normative / 后续产品与体验修改的默认验收标准  
> 更新日期：2026-08-15

## 0. 这份文档解决什么问题

这份 SPECS 不是功能列表，也不是设计灵感记录。它定义的是：**什么样的“不吃亏”才算一个完成度高、视觉层次清晰、可直接行动的产品。**

后续新增 Case、修改内容、重做页面、调整交互或视觉时，默认必须先满足本文，再进入实现细节。不要因为某次修改只涉及文案、CSS 或一个组件，就忽略整体产品体验。

本文回答四个核心问题：

1. 什么叫 **完整产品感**；
2. 什么叫 **正确的信息层级与页面节奏**；
3. 什么叫 **属于 Buchikui 的设计风格**；
4. 一个修改怎样才算 **真正完成**，而不是“代码已经改了”。

### 文档优先级

当文档之间出现冲突时，默认优先级为：

1. `docs/product-experience-spec.md`：产品体验与质量标准；
2. `docs/design-system.md`：颜色、字体、组件、响应式等视觉实现规则；
3. Case 数据与页面实现：具体内容和代码。

如果确实需要突破本文规则，应当把它作为明确的产品决策记录，而不是在实现中悄悄偏离。

# 1. 产品定义

## 1.1 产品不是“法律百科”

“不吃亏”是一个 **消费风险识别 + 证据留存 + 行动路径** 产品。

它不是：

- 法律法规全文索引；
- 情绪曝光平台；
- 律师事务所官网；
- 政务办事门户；
- 只讲原则、不告诉用户下一步怎么做的知识文章。

用户来到页面，不是为了学习完整法律体系，而是为了尽快回答：

> **我遇到的到底是什么问题？现在先做什么？什么证据最重要？该找谁？我要怎么说？**

只要页面不能快速回答这五个问题，即使内容法律上正确、视觉上漂亮，也不算完成。

## 1.2 产品承诺

每个 Case 都应该把一场混乱的消费纠纷，转化成一条可执行的链条：

**识别场景 → 固定事实 → 保存证据 → 要求书面依据 → 选择处理渠道 → 明确诉求**

用户离开页面时，应比进入页面前更清楚三件事：

- 哪些事实真正重要；
- 哪些材料值得立即保存；
- 下一步具体做什么。

# 2. 完整产品感（Product Completeness）

“完整产品感”不是页面更长，也不是功能更多。它来自**闭环**。

一个 Standard Case 默认应让用户完整经过以下体验：

1. **Hero：我为什么应该继续看**
2. **Immediate Actions：如果事情已经发生，我现在先做什么**
3. **Scenario Locator：我遇到的是哪一种问题**
4. **Scenario Guidance：这个问题的关键事实与立即动作是什么**
5. **Evidence：我到底要保留哪些材料**
6. **Escalation Route：如果协商不成，我接下来找谁**
7. **Communication Template：我怎么把问题写成可处理材料**
8. **Sources / Disclaimer：这些判断依据什么，边界在哪里**

这八层不是为了结构完整而机械堆砌，而是构成用户从“发现问题”到“可以行动”的最小完整闭环。

## 2.1 完整度验收问题

一个 Case 发布前，必须能对以下问题回答“是”：

- 用户能否在首屏理解这个 Case 解决什么问题？
- 用户能否在 10–20 秒内找到与自己最接近的场景？
- 用户能否知道**现在马上应该做的第一件事**？
- 用户能否知道最重要的证据是什么，而不是被一长串清单淹没？
- 用户能否区分平台、实际商家、监管部门、法院等不同角色？
- 用户能否得到一个可以直接复制/改写的书面沟通结构？
- 页面是否提供了足够可信的官方依据，同时避免把案例结论泛化成绝对规则？
- 页面从头到尾是否像同一个产品，而不是几段独立文章拼接起来？

任何一项明显缺失，都属于“产品未闭环”。

# 3. 信息架构：场景优先，而不是抽象分类优先

## 3.1 用户从“我遇到了什么”进入

复杂消费纠纷默认采用 **Scenario-first**。

优先使用：

- 到店没车
- 临时换车
- 被验损扣钱
- 重复购买保障
- 出险被拒赔

而不是先要求用户理解：

- 履约问题
- 主体关系
- 责任归属
- 授权结构
- 费用合法性

这些抽象判断可以存在，但应当作为**场景内部的关键事实**，而不是用户进入页面的第一层分类。

### 原则

> **用户语言负责入口，专业判断负责解释。**

## 3.2 场景数量不追求少，也不追求多

不要为了“页面短”强行把多个明显不同的用户问题压成一个抽象大类；也不要因为发现一个新案例，就机械新增一个场景。

新增场景的判断标准：

**只有当它会改变用户的动作、证据或处理路径时，才值得独立成为场景。**

如果新信息只是加强已有判断，应更新已有场景，不新增长度。

## 3.3 单个场景默认只保留两层

Standard Case 中，一个场景默认使用：

- **关键事实**：真正改变判断的事实；
- **现在做什么**：用户可立即执行的动作。

原则上不要重新膨胀成“背景 / 法律解释 / 举证 / 风险 / 建议 / 延伸阅读”六段式小文章。

特殊法院案例、监管案例可以作为关键事实的一部分，但必须服务于用户判断，不能喧宾夺主。

# 4. 内容质量标准

## 4.1 关键事实必须有决策价值

保留一句话前，先问：

> 如果删掉这句话，用户的“找谁、留什么、付不付、怎么追”会改变吗？

如果不会改变，优先删。

页面不是百科，也不是展示研究工作量的地方。

## 4.2 行动必须具体

避免：

- “注意保留证据”
- “依法维权”
- “与商家协商”
- “必要时投诉”

优先：

- “让门店或平台书面确认无法按订单提供车辆”
- “拍车牌 + 行驶证”
- “要求提供书面拒赔理由并指出具体条款”
- “保存当时版本的信用免押协议和实际扣款流水”

行动描述应该尽量包含：**对象 + 动作 + 需要得到/保存的结果**。

## 4.3 不允许内部编辑说明进入用户页面

严禁出现：

- “旧版保留了……”
- “新版压缩为……”
- “这里不再堆场景……”
- “我们选择将……”
- “为了保持页面长度……”

用户只需要知道产品结论，不需要知道我们的编辑过程。

## 4.4 法律与监管表达

涉及法规、政策、法院案例时：

- 当前规则、主管部门、投诉入口必须在修改时核验；
- 优先使用政府、法院、监管机构等一手来源；
- 个案判决不得泛化为“所有类似情况都一定如此”；
- 明确区分不同法律问题，例如“用户是否承担损失”与“平台是否有权直接扣款”；
- 当事实或规则有条件限制时，直接写进正文，不依赖免责声明兜底。

### 文案语气

应当：

- 冷静；
- 准确；
- 有立场但不过度煽动；
- 直接告诉用户风险在哪里。

不要：

- 用“黑心”“坑死”“怒了”等情绪化流量文案；
- 把复杂法律结论写成绝对口号；
- 大量复制法规原文。

# 5. 页面层次与阅读节奏

Buchikui 的视觉层次必须让用户**不读全文也能理解页面结构**。

## 5.1 一级层次：页面主张

Hero 只承担两件事：

1. 一个强、短、可记忆的主张；
2. 标题下第一段用 2–4 句完成问题定性，让第一次进入页面、没有任何背景知识的用户立即知道：**发生了什么 / 为什么和自己有关 / 本文具体解决什么。**

标题下第一段必须**开门见山，而不是直接给操作建议**。不要以“先别……”“先查……”“你应该……”作为第一句话，除非此前已经有一句完成问题定性。

推荐结构：

- 政策 / 收费类 Case：**规则或政策变化 → 现实执行落差 → 本文处理目标**；
- 服务纠纷类 Case：**正常应发生什么 → 实际可能在哪一步失灵 → 本文帮助用户定位和处理什么**。

Hero 不承担完整教育任务。第一段只负责把读者放进正确语境；完整法条、例外、证据和操作步骤进入后续层级。

好的 Hero 类似：

> **租车维权，不靠吵。靠证据链。**

而不是把四五个抽象概念全部塞进标题，或者标题之后马上跳进“先做什么”。

## 5.2 二级层次：立即行动

首屏的深色行动区域必须和 Hero 形成明显视觉反差。

它回答：

> **事情已经发生，现在先做什么？**

行动数量通常控制在 3–4 条，必须是跨场景都成立的高优先级动作。

## 5.3 三级层次：问题定位

Scenario Locator 是“目录”，不是装饰。

用户应该能通过它快速跳到自己的问题。

视觉上：

- 是一条轻量索引轨道；
- 不做大量 pill；
- 文案使用用户自然语言；
- 当前 Case 如果场景多，目录的价值反而更高，不能因为“页面看起来简洁”而删掉。

## 5.4 四级层次：场景正文

场景列表应该具有明显的编辑排版感：

**编号 / 问题标题 / 判断与动作**

每个场景之间通过规则线、留白和编号区分，不依赖卡片边框制造层次。

## 5.5 五级层次：证据区

Evidence 应当是页面第二个明显的视觉锚点。

它不是普通正文继续向下排，而是通过深色整段区域告诉用户：

> **接下来从“理解问题”切换到“保存材料”。**

## 5.6 六级层次：路径与模板

Route 应像一张处理流程表；Template 应像一张可以真正拿去使用的文件。

二者视觉语言不能与场景正文完全相同，否则页面会变成连续长文。

# 6. 视觉风格

## 6.1 核心风格

Buchikui 的视觉定位固定为：

> **Editorial Field Guide / Case Dossier / 消费事故现场手册**

关键词：

- 编辑部排版；
- 案卷索引；
- 高可信度；
- 有态度但克制；
- 强信息层次；
- 少 UI chrome。

不是：

- SaaS Dashboard；
- Bento Grid；
- 政府门户；
- 律师官网；
- 小红书信息卡合集；
- 大量 rounded cards 的消费 App。

## 6.2 层级优先于装饰

设计质量主要来自：

1. 字号差；
2. 字重；
3. 留白；
4. 分隔线；
5. 黑 / 纸色 / 红 / 黄之间的语义对比。

不是来自：

- 更多圆角；
- 更多阴影；
- 更多 icon；
- 更多颜色；
- 更多卡片。

## 6.3 颜色语义必须稳定

继续遵守 `docs/design-system.md`：

- **Ink / Dark**：权威、正文、行动区；
- **Red**：风险、Case 编号、品牌识别；
- **Yellow**：证据、关键事实、选中态；
- **Blue**：规则、行政路径、焦点提示；
- **Paper / Surface**：阅读与文档背景。

不要因为新 Case 有不同主题就重新发明一套配色。

## 6.4 卡片使用规则

默认不使用“每一块内容一个圆角卡片”。

只有当内容确实需要表达：

- 抬升层级；
- 可操作表面；
- 弹层；
- 独立文档；

才允许使用 Surface + border/shadow。

场景列表、Route、Evidence 均优先使用开放排版和分隔结构。

# 7. Standard 与 Compact 页面模式

## 7.1 Standard Case

适用于：

- 存在多个真实用户场景；
- 不同场景的证据或行动明显不同；
- 需要完整的协商 → 监管 → 诉讼路径。

默认结构：

**Hero → Immediate Actions → Scenario Locator → Scenarios → Evidence → Route → Template → Sources**

Standard 不等于“长”。长度取决于场景数量，但单场景必须保持短。

## 7.2 Compact Case

适用于：

- 问题本质上是一个资格判断；
- 用户路径高度线性；
- 3–4 步已经足够完成闭环。

默认结构：

**Hero → 判断条件 / Immediate Actions → 3–4 步路径 → Sources**

不要为了“统一结构”强迫 Compact Case 增加 Evidence、Template 或多个 Scenario。

## 7.3 禁止新增第三种页面模式，除非确有稳定的新问题类型

不要因为单个 Case 特殊，就复制页面或发明一次性 renderer。

先判断 Standard / Compact 是否已经足够。

# 8. 移动端标准

移动端不是桌面版缩水，而是主要使用场景之一。

必须满足：

- `390px` 宽度无横向溢出；
- Hero 标题仍具有强识别度，但不能挤压正文到不可读；
- Scenario Locator 可横向滚动或以清晰方式访问；
- Scenario 正文单列，不产生过深嵌套；
- Evidence 元数据不挤压主标题；
- Route 变为明确纵向流程；
- Case Switcher 固定于 viewport，不受 header containing block 影响；
- 底部操作不会遮挡主要内容；
- focus、点击目标、滚动和分享在触屏下可用。

移动端不能通过“隐藏关键内容”来解决布局问题。

# 9. 交互与行为标准

## 9.1 Case 切换

- 首页随机进入 Case 是产品特性，不是临时 Demo 行为；
- 分享当前 Case 必须生成固定可复现链接；
- 用户通过固定链接进入后切换 Case，应继续保持明确 URL 状态；
- Case Switcher 必须让用户知道当前 Case 和可切换对象。

## 9.2 Evidence 状态

- 勾选状态按 Case 独立保存；
- 用户切换 Case 后不能串状态；
- Evidence 的交互价值是帮助用户形成“准备度”，不是为了增加互动感。

## 9.3 分享 / 打印 / 复制

这些不是附属按钮，而是使用闭环的一部分：

- 分享：把同一个 Case 发给同行人或当事人；
- 打印 / PDF：在现场、投诉或整理材料时使用；
- 复制模板：把阅读直接转成沟通行动。

后续视觉调整不得让这些能力难以发现或失效。

# 10. 技术与架构约束

当前架构原则继续保持：

- 纯静态站；
- Case 数据与 renderer 分离；
- Standard / Compact 两种明确模式；
- 共用设计系统和交互；
- 不为单个 Case 复制页面；
- 不为了一个文案问题新增框架、配置层或依赖。

新增功能时优先检查现有结构是否已经能表达需求。

### 不接受的实现方式

- 为了兼容旧数据保留两套字段和 fallback；
- 新旧 renderer 长期并存；
- 一次性 CSS override 越叠越多；
- 为单个 Case 创建专属页面壳；
- 只为了未来可能需求建立复杂 schema；
- 明知结构不合适仍“先这样以后再换”。

如果产品决策发生变化，直接更新主结构，不保留过时兼容层。

# 11. 反退化规则（Anti-regression）

以下情况即使实现正确，也视为体验退化：

## 11.1 从用户场景退化为抽象分类

例：把“到店没车 / 临时换车 / 出险拒赔”合并成“履约 / 车辆 / 保障”三个抽象入口，导致用户需要先学习我们的分类。

## 11.2 为了短而失去闭环

删掉 Evidence、Route 或 Template，使页面变成“几个知识点”。

## 11.3 为了完整而无限增长

每发现一个新闻、案例、判决，就新增一个 Scenario 或证据项。

## 11.4 把研究过程写进产品

出现“旧版 / 新版 / 我们压缩 / 我们保留”之类内部说明。

## 11.5 视觉重新 SaaS 化

大量圆角卡片、pills、渐变、图标面板，让页面从编辑式现场手册变成通用 Dashboard。

## 11.6 视觉层次被拉平

Hero、场景、Evidence、Route、Template 看起来都是同样字号、同样背景、同样卡片，用户无法通过扫视理解结构。

# 12. Definition of Done

一个面向用户的修改，只有同时通过以下四个 Gate 才算完成。

## Gate A — Product

- [ ] 用户能快速知道页面解决什么问题
- [ ] 标题下第一段无需背景知识即可说明“发生了什么 / 为什么和用户有关 / 本文解决什么”
- [ ] 用户能通过自然语言场景找到自己
- [ ] 页面提供明确的立即动作
- [ ] 证据、路径、模板形成行动闭环
- [ ] 没有为了短而牺牲关键场景
- [ ] 没有为了完整而重复堆内容

## Gate B — Content

- [ ] 每个场景只保留会改变判断/行动的关键事实
- [ ] “现在做什么”具体到对象、动作、结果
- [ ] 没有内部编辑说明
- [ ] 法律/监管/案例表述有边界，不做不当泛化
- [ ] 当前渠道、法规、主管部门在需要时已核验
- [ ] Sources 能支撑主要结论

## Gate C — Visual / UX

- [ ] 首屏具有清楚的 Hero → Immediate Actions 层次
- [ ] 用户扫视即可识别 Scenario / Evidence / Route / Template
- [ ] 没有重新引入 card-everything / pill-everything
- [ ] 色彩语义符合设计系统
- [ ] 桌面和 390px 移动端都无横向溢出
- [ ] 移动端没有通过隐藏关键内容“解决”布局
- [ ] focus / reduced motion / keyboard 等基础可访问性未退化

## Gate D — Functional / Technical

- [ ] Base URL 随机 Case 行为正常
- [ ] 固定 `?case=` 分享链接正常
- [ ] Case Switcher 正常
- [ ] Evidence 状态按 Case 保存
- [ ] 分享、打印、复制模板正常

# 13. PR 自检模板

后续涉及用户体验的 PR，描述中至少回答：

### Product effect

- 用户原本遇到什么问题？
- 修改后用户更快完成哪一个判断或动作？
- 是否改变了页面长度、场景数量或闭环？为什么？

### Visual effect

- 修改影响了哪一级视觉层次？
- 是否仍符合 Editorial Field Guide / Case Dossier 风格？
- 是否在桌面和移动端检查过？

### Content effect

- 新增内容是否真正改变用户行动？
- 如果只是加强已有判断，为什么没有新增场景？
- 主要事实依据是什么？

### Regression check

- Case Switcher / share / print / evidence / template 是否仍正常？
- 是否出现内部编辑说明、重复内容或抽象分类替代用户场景？

如果 PR 无法说明它如何改善用户判断或行动，应重新考虑这个改动是否值得进入产品。

# 14. 一句话质量标准

未来任何 Buchikui 页面都应达到下面这个效果：

> **第一眼像一个有明确主张的成熟产品；标题下第一段马上说清这是什么问题；扫一眼能看出信息层次；找到自己的问题后马上知道做什么；继续往下能把证据、渠道和沟通方式完整走通。**

视觉上保持 **编辑式现场手册的可信与克制**，内容上保持 **场景优先、关键事实优先、行动优先**。

这就是“不吃亏”的默认质量线。

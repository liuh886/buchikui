# 不吃亏 / Buchikui — Product Experience SPECS

> 版本：v1.4  
> 状态：Normative  
> 更新日期：2026-08-21

## 1. 产品定义

“不吃亏”是一个 **消费风险识别 + 动态权利更新 + 证据留存 + 行动路径** 产品，不是法律百科、政务门户、法律新闻站或长篇知识文章。

用户来到一个 CASE，只需要尽快回答六个问题：

1. 我遇到的是什么问题？
2. 最近有没有新规则改变我的权利位置？
3. 现在先做什么？
4. 哪些事实会影响责任判断？
5. 哪些证据要马上保存？
6. 协商不成下一步找谁、怎么说？

页面不能因为追求“完整”而把这些问题埋进目录、说明、标签和重复章节里。

### Living CASE

每个 CASE 都是会随法律、监管、司法解释、平台规则和高价值裁判变化而更新的 **Living CASE**。

法律更新不是单独的新闻栏目。公开页只展示当前对该 CASE 最有行动价值的一条“权利更新”，并完成这次翻译：

**新规则 / 新裁判 → 消费者多了什么权利 → 对方少了什么借口 → 现在可以要求什么。**

默认只保留 1 条最强更新，并显示最近核验日期。更完整的来源继续留在 Sources，不把正文变成法规时间线。

法律新鲜度、来源权重和裁判引用纪律以 `docs/legal-freshness-standard.md` 为准。

## 2. 唯一阅读路径

Standard CASE 默认只有一条主路径：

**一句主张 → 当前权利更新 → 3–4 个立即动作 → 场景列表 → 关键证据 → 处理路径 → 按需模板 → 来源 → 最终经验**

其中：

- 当前权利更新只保留一条最强、最可执行的信息，不建立法律资讯流；
- 场景列表本身就是“找到我的问题”，默认不再单独增加 Scenario Locator；
- “正常服务基线”等辅助判断模块只有确实必要时存在，并默认折叠；
- 沟通模板属于工具，不占据默认阅读主线，默认折叠；
- Sources / Disclaimer 留在底部，不与行动内容争夺视觉层级。

不要新增第二套目录、重复 CTA、独立 dashboard、说明性 chrome 或只用于解释页面结构的 UI。

## 3. Header

Header 只保留：

**品牌 / 当前 CASE 切换 / 分享**

Case Switcher 的关闭状态只显示 **当前 CASE 名称 + Chevron**。CASE 编号、英文标签、随机入口等信息只在展开后的案例目录里出现。

不再提供常驻的“典型场景 / 证据 / 路径 / 模板”页内导航。页面本身是一条线性行动路径。

## 4. Hero、权利更新与立即行动

### Hero

Hero 只承担两件事：

1. 一个强、短、可记忆的主张；
2. 一段问题定性，让第一次进入页面的用户立刻知道发生了什么、为什么与自己有关、本文解决什么。

Hero 不再重复显示 CASE stamp、目录提示或下一步导航。

### 当前权利更新

Hero 后允许存在一条轻量 `rights pulse`，只回答：

**最近哪条有效规则 / 高价值裁判改变了我现在可以要求什么？**

它必须：

- 显示来源权重，例如 `司法解释 / 部门规章 / 监管典型案例`；
- 显示法律核验日期；
- 用自然语言给出一条当前可执行动作；
- 优先链接官方 / 一手来源；
- 不重复 CASE 正文已经完整解释的背景。

它不能：

- 变成法律新闻列表；
- 同时堆 3–5 条更新；
- 用普通个案判决写成普遍法律结论；
- 只摘法条、不告诉用户下一步做什么。

### Immediate Actions

通常保留 3–4 项跨场景都成立的高优先级动作。

默认只展示动作标题；详细解释放到后续场景、证据或路径中。只有标题本身无法避免用户做错关键动作时，才增加一行必要说明。

## 5. 场景是核心单位

复杂纠纷继续采用 **Scenario-first**。

场景标题使用用户自然语言，例如：

- 到店没车
- 临时换车
- 被验损扣钱
- 重复购买保障
- 出险被拒赔

每个 Standard CASE 场景默认只保留：

- **关键事实**：真正改变责任、证据或金额判断的事实；
- **现在做什么**：对象 + 动作 + 要得到 / 保存的结果。

默认不再单独显示 `risk` 副标题。`short` 只作为内容数据中的稳定场景名称，不再额外制造一个可见层级。

只有当新信息会改变用户动作、证据或处理路径时，才新增场景。

## 6. Progressive Disclosure

Buchikui 默认采用“主线展开、辅助信息收起”。

### 默认展开

- Hero
- 当前权利更新
- Immediate Actions
- 场景正文
- Evidence
- Route
- Sources / Takeaway

### 默认折叠

- 正常服务基线等辅助背景模块
- Communication Template

折叠不是删内容。会决定投诉、调解或诉讼结果的事实仍然必须保留，只是不让辅助信息抢占第一阅读层。

## 7. Evidence

Evidence 保留可勾选状态和进度。

每项只显示：

**材料名 + 必要的一句用途说明 + 确有价值时的时间提示**

分组可以保留，但分组说明默认不显示。不要把证据清单写成第二篇文章。

新规则改变举证责任时，Evidence 应优先告诉用户：**证据在谁手里，以及应该向谁明确索取。** 不再默认所有证据都由消费者自己想办法寻找。

## 8. Route

Route 是简洁的升级路径，不是新的大章节。

每一步回答：

**什么时候升级 → 找谁 → 带什么 → 要什么结果**

默认不再额外显示 kicker 和长篇 section intro。重要条件可以留在 step 或 route note。

监管或申诉规则有明确前置投诉要求、答复期限或受理时限时，必须保留，因为错过可能直接改变用户的救济位置。

## 9. Template

模板默认折叠，只露出明确的“查看 / 复制”入口。

展开后保留：

- 必要的一句使用说明；
- 完整模板正文；
- 复制操作。

不要为了展示工具而让模板永久占据整屏。

当新规提供了新的程序权利，例如要求平台说明事实 / 理由 / 依据、要求人工复核、要求提交其控制的证据，模板应优先把这些权利翻译成可以直接复制的请求。

## 10. Compact CASE

Compact CASE 继续保持：

**一句主张 → 当前权利更新 → 判断 / 条件 → 3–4 步处理 → 必要说明 → 来源 → 最终经验**

不要为了和 Standard CASE 形式一致而补齐无用模块。

## 11. 移动端

移动端优先保证：

- 首屏能看到主张和立即动作；
- 当前权利更新保持一条短信息，不制造新的卡片流；
- Header 只保留品牌 + CASE 名称；
- 底部操作只保留“找到我的问题 / 查看处理步骤”和“分享 CASE”；
- 390px 宽度无横向溢出；
- Case Switcher 使用底部抽屉；
- 折叠模块使用原生 `details/summary`，键盘和触摸均可操作。

## 12. 发布前验收

发布或修改 CASE 前只检查：

1. 首屏是否马上说清这是什么问题；
2. 当前权利更新是否真会改变用户动作，而不是为了显得“新”；
3. 默认可见层是否只有一个阅读主线；
4. 每个场景是否仍然是“关键事实 + 现在做什么”；
5. 是否保留了会改变责任、证据、损失金额或诉讼结果的关键节点；
6. 是否检查了当前有效规则、新近司法解释 / 部门规章 / 高价值裁判；
7. 辅助说明是否能折叠或删除，而不是继续 append；
8. 用户是否能顺着页面完成“判断 → 留证 → 升级 → 表达诉求”的闭环。

核心原则：

> **简化解释，不简化决定结果的过程；更新法律，不堆积法律。**

## 3. 发布前应修的确认问题

### R1：新画像机制与缺答覆盖仍混用两套分组

位置：[survey-portrait.js](../../survey-portrait.js:45)。

`calculate`先按旧journeys（旅游/预付/售后）判断覆盖，再按新mechanisms分类。新画像契约要求每个机制至少一题非skip，两者不等价。

| 第1至8题选择 | 按新契约应有结果 | 当前实际结果 |
| --- | --- | --- |
| YES / skip / NO / NO / skip / NO / YES / NO | 新机制B的Q2、Q5全跳过，应为覆盖不足 | 小海獭，正常分类 |
| skip / skip / NO / NO / YES / NO / NO / NO | 非skip共6题，A/B/C均有回答，B有一个YES，应可为小水豚 | 小云朵，因旧旅游组全跳过被拒 |

第二种已在真实浏览器中复现，见[覆盖误判截图](../../docs/prototype-assets/2026-10-24/iteration-2-independent-review/04-coverage-mismatch.jpg)。这会同时产生错误放行与错误拦截，不是单纯文案问题。

**修复标准：**统一依据最终确定的画像机制做覆盖、比较和解释；增加上述两个方向的回归测试。旧消费主题仍可用于记录和阅读组织，但不得偷偷充当另一套画像门槛。

### R2：并列结果未覆盖两个胜出机制，原错位问题只修了一部分

位置：[survey-portrait.js](../../survey-portrait.js:82)。

沿用原复现输入`NO/YES/YES/NO/NO/YES/YES/YES`：

- 新规则A为Q7/Q8，2/3；C为Q3/Q6，2/3；B只有Q2，1/2，结果为狐狸。
- 当前画像依据列出Q7、Q8、Q3、Q6。
- 第一则推荐Q3健身结算，属于胜出C，较原版有改善。
- 第二则却是Q2酒店预扣，属于未胜出的B，没有回应另一个胜出A。

原因是第一则之后仍按旧groupId和全局priority选第二则，没有按并列机制选取。契约所说的“两条并列机制各取一条线索/案例”尚未落地；理由也仍扁平列出全部命中项，没有区分并列方向。

**修复标准：**画像输出明确胜出机制及各自证据。并列两种机制且均有候选时，两则分别回应两个胜出方向；三个机制并列时写清优先和后续查阅规则。测试不能只断言第一则在reasonQuestionIds里。

### R3：浏览器的机制配置准入未随新模型补齐

位置：[survey-portrait.js](../../survey-portrait.js:7)、[portrait-content.mjs](../../scripts/lib/portrait-content.mjs:79)。

在独立VM中复制当前公开内容，把第一机制的questionIds改成不存在的题号：前端validate仍返回空错误列表，installContent返回true。只选原Q1为YES的完整答卷随后得到狐狸、reasonQuestionIds为空。

构建端会拒绝不存在/重复题号，这一点已核对，不能说所有准入均失效；缺口在浏览器损坏载荷的原子拒绝。构建端也应明确portrait-2必须有机制、全部公开题的机制归属完整，避免缺配置时静默回退旧模型。

**修复标准：**构建和浏览器对机制存在性、非空、ID/角色唯一、题号有效及完整覆盖保持一致；坏载荷保留旧问题和旧画像整包。追加机制损坏测试，不能只复用旧groups损坏测试。

## 4. 产品层面仍需收尾的地方

1. **机制改了，角色名没跟上。**电池换新和二手假货现在可能得到“旅途小海獭”，虽有机制解释，名称仍暗示旅游。需要让名称、角色短句、解释和实际证据一致；不是只把算法名换掉就能称画像辨识已彻底解决。
2. **结果有重复表达。**本轮狐狸的description与reason为同一句，连续显示两遍。建议一句承担角色表达，另一处给出实际差异化依据。
3. **短屏通过的代价是题目明显缩小。**实测短屏主问句18px，常规手机21px，原版手机31px。操作区确实修好，但纸牌仍有较多空白，可以继续用空间重排改善阅读，不宜只以按钮未越界宣布最优体验。
4. **题面校准仍是候选。**公开八题及语义版本没有改动，健身赠送条件、相邻停业题、写真复合条件、电池对象等问题仍在。保留旧版本是允许的，但F05应为“候选已准备、真人理解待验证”，不是已消除。
5. **无YES且有skip的角色描述需更准确。**UI理由用“未报告”较妥，bird公共description仍写“你暂时都没有遇到过”。有skip时不能替未回答题作结论，角色卡也会使用此description，应统一为“本次没有报告这些遭遇”。

## 5. 测试证据应如何理解

88项Node测试是真实通过，构建与契约也通过。但`npm test`没有执行Python浏览器脚本，不应写成“88项单元与端到端全部通过”并把二者混在一起。

`verify_iteration_2_ui.py`对390×844提醒底部有断言；390×666结果页仅打印位置和检查横向溢出，没断言提醒底部。320×640只检查首题一个回答按钮，未走到最长题。旧结果标签和reason只来自YES的穷举仍不能验证新机制覆盖门槛、并列方向与损坏机制配置，所以88绿测与R1–R3能够同时存在。

建议补“机制全skip但旧组不空/旧组全skip但机制不空”“并列两方向各有案例”“坏机制整体拒绝”，再补全短屏各状态的精确断言。真实用户喜欢、读屏输出及真机系统分享仍需真人/设备证据，不由测试数量证明。

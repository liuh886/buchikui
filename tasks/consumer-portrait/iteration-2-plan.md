# 第二轮工作计划：让画像有辨识，让案例有回报

日期：2026-10-24。状态：产品规划已形成，以下开发与用户验证均未执行。  
输入：[产品经理完成度评估](../../docs/consumer-portrait-pm-assessment.md)、[PRD基线](../../docs/consumer-portrait-prd.md)。  
本轮目标：从“功能已交齐”推进到“用户看得懂角色、获得具体提醒、能顺畅操作，具备进入发布验收的条件”。

## 1. 本轮产品决定

1. 继续做**消费经历画像**，保留亲身遭遇、YES/NO等权、跳过、无判分。角色描述本次记录，不测心理人格、消费能力或成熟度。
2. 画像从“旅游/预付/售后哪个题组YES多”转向验证“不同场景里出现了什么共同经历”。先完成内容证据与结果样例，再定映射；不能只换动物名字继续原分类。
3. 复用六套正式插画及现有静态架构；角色名、短句和映射允许调整。六张图不要求硬凑六种同层级类型，未报告与信息不足应明确是两种结果状态。
4. 默认不增加题量。现有八题逐项校准，必要时替换重复或难理解题；新题仍须有直接支持的核验案例，语义变化升版本。
5. 结果首屏同时兑现可爱角色与一条具体提醒。分享保留，但不成为用户获得收获前的唯一主行动。
6. 集中云收集、消费等级、角色扩容、复杂CMS和大规模推广仍在本轮范围外；不能用这些工作替代核心体验收尾。

## 2. 完成目标与范围

| 必须兑现的目标 | 本轮可检验的结果 |
| --- | --- |
| 我能认出自己的角色 | 用户能根据具体经历解释角色，并说明与另一角色的区别，不只复述题组名称 |
| 我确实带走一点教训 | 结果先给一条能复述的提醒，相关案例与本人记录和主画像对齐 |
| 我能轻松填完 | 短屏主要回答完整可见，问句没有反复出现的关键误解 |
| 内容能被稳定生产 | 来源变更和短读改写均触发重审，一批内容有真实编辑、审核、验证记录 |
| 发布决定有证据 | 自动、浏览器、真机、读屏和用户理解分开记录，缺哪项就保留哪项 |

本轮必须做：F01画像定义、F02推荐对齐、F03短屏、F04结果首屏、F05问句校准、F06改写重审，以及T13/T15真实验收准备与实际执行。

本轮可延后：F08结果直接定位修改；分享文案的额外花样；新增插画；新消费领域扩题。F07分享动机纳入观察，不以增加分享入口解决。

## 3. 阶段与依赖

| 阶段 | 工作 | 主要负责角色 | 交付与退出条件 |
| --- | --- | --- | --- |
| A 产品与内容校准 | 经历特征、题目覆盖、角色样例、结果层级 | 产品牵头，编辑/设计/架构参与 | G1：证据能支持角色，三个差异清楚的样例及两类兜底齐备 |
| B 核心体验改进 | 新映射、推荐、短屏、首屏提醒、改写重审 | 开发牵头，产品/编辑复核 | G2：可运行版本，已知复现全部通过，不损坏旧回答 |
| C 用户与实机验证 | 逐题复述、角色理解/喜好、实际收获、读屏/分享 | 产品组织，实际测试者执行 | G3：原话与设备证据齐全，失败项修订复查 |
| D 发布准备 | 版本、验收结论、完整包回退与复盘安排 | 开发/产品 | G4：发布门槛满足，形成可审查发布包；是否已发布单独记录 |

A阶段未闭合时，短屏修复、重审门禁和测试准备可以先做；角色映射和最终推荐不得抢先固化。结果页布局可用既有真实案例做原型，最终文案与画像需跟随A阶段结论。C阶段可分批发现问题，正式验收须针对最后一版复查。

这里采用阶段门槛而非承诺日历工期。真实受访者与设备安排影响C/D，不能把等待算成已经验收；人员与设备明确后再排具体日期。

## 4. A阶段：先把画像做对

### N01 经历特征与题目覆盖表

负责人：产品＋编辑。优先级：最高。对应F01/F05。

每题登记：实际在问什么、可支持的经历特征、不能支持的推断、与其他题重复之处、可带走的提醒。优先研究三类候选：**承诺与实际不符、服务安排被改变、售后/结算受阻**；它们是待验证的经历机制，不是已确定的新消费者类型。

一题可有多个编辑标签，但最终归类不能重复计分制造偏向。核对标签覆盖不均，不能把现有2/3/3题组比例直接换成标签比例。新维度若只有一条窄场景支持，就先合并、作为辅助线索或保留不确定，不硬做独立类型。

交付：`iteration-2-experience-matrix.md`，包含保留/改写/替换建议及排序理由。问句改写或新场景进入实现前，按四份内容权威规范核验来源，不能在规划标签时顺便发明案例。

### N02 画像解释与角色样例

负责人：产品＋设计；架构核对可计算性。依赖N01。

交付：`iteration-2-portrait-contract.md`，至少包括三个有区别的结果样例、混合经历、无报告、覆盖不足、并列、只一项YES的处理。每个样例有：

- 可爱名称和一句易记的描述；
- 两条直接来自本次有效回答的线索；若不足两条，明示线索有限，不补造；
- 一条有对应案例和边界的提醒；
- 与其他角色的区别、允许与禁止的解释；
- 输入答卷、预期结果、推荐原案及规则版本。

文案方向演示：用“这次记录里，说好的与实际给的出现了落差”，而不是“你天生容易相信别人”；用“几件不同消费，都遇到服务安排变化”，而不是“你总爱折腾”。演示不是已审核法源或最终角色定义。

架构随后补确定性规则、证据选择、覆盖门槛、并列处理和版本迁移。分类依据必须能解释，不能用运行时自由生成或看不见的随机性装出个性化。

**G1退出：**产品逐份核对样例能由答卷支持、角色之间有可说明的区别、没有能力推断；架构确认可实现。若现有题目支持不了更丰富画像，先完成题目/画像模型调整，不让开发用包装文案掩盖。G1为内部交付检查，不代替C阶段真实用户验证。

### N03 问句与结果页原型校准

负责人：产品＋设计。依赖N01/N02，可与架构细化并行。

重点：健身题的复合条件、两道停业题重复、写真多条件、电池商品对象、二手假货判断。先做候选表达与来源边界核对，不直接替换公开题面。入口保持直接进首题，不新增介绍门槛。

结果首屏目标结构：角色形象/名称 → 一句本次经历解释 → 一条具体提醒及对应案例入口 → 角色卡保存作为次行动；完整原案、其他回报与记录在下方。可爱主体不取消，减少泛化重复和空白。至少出正常角色、未报告、覆盖不足三种状态，覆盖390×666和390×844。

交付：可比较的结果原型与题面候选；使用现有正式素材，不先生成新角色。

## 5. B阶段：开发任务与验收

| 编号 | 任务与负责角色 | 依赖 | 具体完成标准 |
| --- | --- | --- | --- |
| N04 | 开发：短屏回答区 | 可先做 | 390×666、390×844、320×640的首题和当前最长题，默认字号下YES/NO完整语义可见，跳过可达；44px目标不缩水，无横向溢出；大字允许纵向阅读 |
| N05 | 开发＋编辑：短读改写重审 | 可先做 | 审核记录同时绑定原案/规则与本次短读文本，正文或提醒修改后原审核失效；明确复核后才能发布，失败保留旧库 |
| N06 | 开发：画像与证据模块 | N02/G1 | 精确实现新合同，覆盖缺答/无YES/并列/单一线索；修改后理由仅取当前响应，旧规则结果不能静默当新结果 |
| N07 | 开发：推荐与主画像对齐 | N06 | 第一则来自画像证据对应的实际YES案例；第二则优先另一项YES，尽量兼顾不同交易场景；没有足够匹配再补中性入门内容 |
| N08 | 开发＋产品：结果首屏与分享衔接 | N03/N06/N07 | 390×666和390×844默认字号下可看到具体提醒或其明确阅读行动；原案必要边界可达，分享卡不带私人答卷内容 |
| N09 | 开发＋编辑：问句及版本集成 | N01/N03；依据早期理解记录修订 | 仅发布核验支持的题面；语义变更升版本，旧回答不混算；原内容和测试数据不污染真实答卷 |

N07不再用“每个journey只能一则”的硬限制挤掉主画像证据：主画像可能跨交易主题。caseId/规则去重继续保留；两则若同机制但都切题，优先保证关联，并由编辑控制重复。并列画像有两个独立证据方向时各取一则，规则在N02写清。无报告和覆盖不足使用中性标题。

必须保留原始复现用例：第1到8题`NO/YES/YES/NO/NO/YES/YES/YES`。若仍使用原画像模型，该答卷必须至少推荐一则购物/售后原案；若按新模型重分类，则第一则必须来自新版主画像的实际证据，不能只更改测试预期绕开错位。

N05的审核字段放内部版本化输入，公开产物只投影正式内容。文本哈希能检出改写，不能证明法律语义正确；必须记录审核角色、时间、范围与结论。不得增加“自动重算所有审核指纹”来绕过人工重审。

**G2退出：**以上任务可运行、独立代码/内容复核完成、旧回答/离线/分享/版本保护无回归；新增测试针对已发现问题，旧87项测试不能当新增功能证据。当前旧模型的穷举测试须随新合同重新审视，不机械复用其分类期望。

## 6. C阶段：用户与设备验证

### N10 六至八人理解与回报测试

负责人：产品；由项目负责人安排参与者，本文不自动招募或发送邀请。经历多/少者都要覆盖，不把法律背景当消费经验。每人约15–20分钟的观察安排是计划值，实际记录为准。

先不给算法或操作讲解，请参与者自然开始；记录题意复述、YES/NO理由、困惑原话、是否主动看案例。完成后问角色为何与自己有关、和另一结果有什么不同、能带走哪条提醒、是否愿意保留角色卡及原因。

不要求试用户透露真实订单、金额或身份；不强制发送角色卡。保存意愿、点击保存、实际外发分开记录，不伪造转化。

按PRD既有门槛，至少`ceil(0.75×n)`位（6人→5、7人→6、8人→6）能独立开始、解释角色与自身记录关系、复述至少一条边界正确的提醒；相同人数愿意保留角色形象。记录失败者的问题，重复关键误解必须修正复查，不能只看人数达标。小样本用于排除体验障碍，不证明市场成功或测量效度。

可先用部分参与者对比A阶段样例，余下或回访用于修订后验证；不能把多个旧版本的好结果拼成最终版本通过。若未安排到真人，继续完成开发与测试准备，状态停在“待验证”，不宣称已验收。

交付：`iteration-2-user-validation.md`，逐项原话、观察、版本、修改与复查决定；样本仅用代号。

### N11 实机、读屏与异常路径

负责人：开发组织，实际设备测试者执行。最终待验版完成后检查：

- 一部真实iPhone Safari及一部真实Android Chrome的点击/滑动、短拖取消、纵向阅读、刷新和案例返回；
- VoiceOver/TalkBack的题目、角色理由、缺答、提醒、原文及弹窗焦点；
- 系统大字/缩放、短屏、减少动态、离线、图像失败；
- 系统分享打开与取消、PNG保存、剪贴板拒绝和手动复制后备。无需给他人发送。

交付：`iteration-2-acceptance.md`，列设备/系统/浏览器/版本/证据，浏览器模拟和真机分栏。没有设备或读屏条件时相应项继续待执行，不以截图代签。

**G3退出：**最终版本的N10/N11记录齐备，阻止理解、填写、查证或退出分享的问题均修复并在对应条件复查；不能只有“测试通过”的一句话。

## 7. D阶段：生产闭环与发布准备

### N12 一个真实内容批次与一个可审查发布包

负责人：产品/编辑/开发。

将本轮至少一条修订题目或案例短读按既有批次模板完整记录：选题理由→原案边界→改写→审核→用户理解→修订复查→构建与验收。若仅调整结果解释，也必须记录证据、审核及理解，不虚构问句改版。

发布包包含提交/版本候选、问卷/画像/内容/素材版本、自动与人工证据、已知未解决事项、完整旧包回退及回答保留策略。同步产品规范、PRD差异、任务与验收状态；不将本轮“计划”写成“已完成”。

**G4退出：**可以给出有证据的通过/不通过结论。条件不足就保持内测，不推动对外发布。实际推送部署按届时任务授权处理；本规划不自动发布。公开发布后才执行首轮效果复盘，没有事件采集时使用实际反馈与观察，不生成虚构数据。

## 8. 负责人、排期与范围控制

产品负责N01–N03/N10及最终验收判断；架构负责N02技术合同与版本设计；开发负责N04–N09/N11/N12的工程交付；编辑负责来源、题面/短读语义和审核；设计负责角色表达与结果层级。可以由同一人/Agent承担多个角色，需区分执行与复核记录，不假称已配齐团队。

关键路径：`N01 → N02/G1 → N06 → N07/N08/N09 → G2 → N10/N11 → G3 → N12/G4`。N04/N05和验证脚本、记录模板准备可先推进。真人早期反馈可穿插A/B，最终G3必须覆盖最后修订版。

若画像定义仍无解释力，回到N01/N02；若题面无法理解，回到N03/N09；若只有分享意愿弱，先检查角色认同与回报，不先加奖励/排行榜。新增任务必须说明修复哪个已识别问题，不能挤占本轮核心收尾。

## 9. 本轮退出清单

- [ ] 画像合同和实例有可核对证据，角色差异不只来自消费题组名称。
- [ ] 主画像、理由、第一则案例与首屏提醒形成同一条阅读路径。
- [ ] 原短屏复现修复，回答语义完整可见，缺答及大字场景合理可达。
- [ ] 重复/复合/窄场景问句完成理解验证，必要改写已有来源与版本记录。
- [ ] 短读自身改写会触发重审；真实审核与内容批次留痕。
- [ ] 最终版用户理解/喜好、真实设备/读屏与自动检查证据齐全。
- [ ] 旧回答与待同步数据保留，测试数据隔离，分享不泄漏私人记录。
- [ ] 发布结论、版本候选与完整包回退明确；未发布时继续如实标注。

本轮成功的标志是核心收益成立且有证据，不是再多做几个功能。云端集中收卷继续属于独立下一阶段。
